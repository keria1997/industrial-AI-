# ISSUE-035：需求澄清——移除岗位概念，角色直接挂账号且一账号一角色

- 级别：P0 模型变更
- 模块：平台管理
- 层级：L4 基础层
- 影响范围：前端, 后端, PRD, 设计文档
- 状态：⏭️ 前端本地已修复，后端单角色契约与部署待联调

## 问题

当前系统引入了"岗位（Position）"概念，通过 `iam_position` 表的 `default_role_ids[]` 实现岗位→角色的间接授权链路。但业务需求澄清后确认：

1. **系统中不存在"岗位"这个概念**
2. **组织和部门用来管理员工**（员工归属组织，不归属岗位）
3. **一个员工只能有一个账号**（1:1 关系）
4. **角色直接挂在账号上**（不经由岗位中转）
5. **一个账号只能有 1 个角色**（非多角色）

这与当前实现存在根本性冲突：

| 冲突点 | 当前实现 | 正确模型 |
|---|---|---|
| 岗位 | `iam_position` 表 + `default_role_ids[]` | **不存在的概念** |
| 角色→账号 | 通过岗位间接继承 + `direct_role_ids[]` 多角色 | 账号必填标量 `roleId`，对应唯一角色 |
| 员工→账号 | 1:1 但可通过多岗位间接多角色 | 严格 1:1 |
| 组织 | 组织→岗位→员工 | 组织/部门→员工 |

## 原因

需求分析阶段错误引入了 HR 系统中常见的"岗位"概念，但本项目为轻量级 B2B ERP，用户管理模型应为扁平化的"组织→员工→账号→角色"关系，不涉及岗位层级。

## 方案

### 后端

| 改动 | 文件 | 说明 |
|---|---|---|
| 移除岗位表 | `iam_position` 表 | DROP 或标记 deprecated |
| 移除岗位种子数据 | `TenantCatalog.java` | 删除 `orgUnits()` 中的岗位定义、`ADMIN_POSITION_ID` |
| 角色改为单选 | 账号数据模型与 API | API 使用标量 `roleId`；数据库迁移与唯一约束由后端实现，不保留多角色数组作为新写入契约 |
| 角色解析简化 | `PlatformService.java` | 移除通过 `position.defaultRoleIds` 获取角色的逻辑 |
| 移除岗位 API | `PlatformController.java` | 删除岗位 CRUD 接口 |

### 前端

| 改动 | 文件 | 说明 |
|---|---|---|
| 移除"新增岗位"弹窗 | `PlatformManagement.tsx` | 删除岗位创建 UI |
| 组织与员工 | `PlatformManagement.tsx` | 组织树维护组织，详情“组织员工”显示直接归属员工与账号角色，无岗位入口 |
| 账号创建和角色编辑 | `PlatformManagement.tsx`、`EmployeeAccountManagement.tsx` | 只允许选择一个启用角色，停用账号仍占用员工绑定，不允许另建账号 |
| 历史数据处理 | `accountRole.ts`、`persistPlatformChange.ts` | 多角色数组及缺失角色明确提示，不自动取首项；回读未确认绑定时不报告保存成功 |
| 审批人解析 | `PlatformManagement.tsx` | 仅支持按角色、按组织负责人；旧解析器提示迁移，候选人预览不等于服务端审批执行 |
| 会话与工作台 | `AppRuntimeProvider.tsx`、`App.tsx` | 展示会话账号角色，未知角色不回退老板；本人角色变更后刷新签名会话和有效权限 |

### PRD

### 设计文档

## 验收标准

1. 系统中不存在"岗位"相关的表、API、UI 组件
2. 组织与部门用于管理员工（员工归属组织，不归属岗位）
3. 一个员工只能有一个账号（数据库唯一约束）
4. 角色直接挂在账号上（不经由岗位中转）
5. 一个账号只能有 1 个角色；账号写入使用标量 `roleId`，禁止多角色数组及前端展示辅助字段
6. 工作台按服务端确认的唯一账号角色及展示分组显示指标；菜单按有效权限集合显示，不能根据角色名称授予权限；未匹配分组时明确不可用，不回退老板
7. PRD 和设计文档中不再出现"岗位"概念

## 进展

### 2026-10-18 前端实施

用户确认后实施，仅修改前端、测试及 Issue 记录；没有修改后端、数据库、PRD 或设计说明书。

- 完成组织、员工、账号、人员档案、工作台、个人信息及消息草稿中的岗位入口和字段清理。
- 员工建档不提交 `primaryPositionId`；账号开户、编辑提交单个 `roleId`。前端阻止同一员工重复开户，包括已有停用账号；数据库唯一约束仍需后端保证。
- 历史 `directRoleIds` 数据显示“历史角色数据待修正”，管理员须明确重选；未知审批来源显示“历史审批规则待迁移”，不自动转换。
- 角色接口成功后回读快照核对绑定；未确认时提示核实，避免假成功。组合开户响应未确认角色时保留一次性初始密码，并提示勿重复创建。
- 当前账号角色变化后刷新签名会话及有效权限；未知/缺失角色不发送老板工作台请求，指标、预警、动态显示不可用。
- 前端类型检查、构建、41 个单元测试文件 / 260 项测试通过；后端只作 `mvn compile -q` 检查，通过。
- Playwright：平台受控验证 10 组、身份受控验证 5 组、工作台回归 7 组、本地真实只读验证 4 组通过。受控业务数据只在测试脚本中，未写入真实业务数据库。
- 部署环境 `https://erp.wanshen.top/` 登录成功，但未出现新的“工作台账号角色”标识，部署验收失败，待发布后复测。
- 工作区另有并行提交及回退：后端单角色修改曾提交后回退；本报告以最终读取到的代码和运行服务为准，不能沿用“后端已完成”的中间结论。
