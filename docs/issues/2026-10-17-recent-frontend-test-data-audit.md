## 2. 正式路径中的问题

以下位置均为审查时源码行号。P1 表示可能影响正式写入或质量办理，P2 表示展示或状态判断风险。

### FD-01 / P1：库存快照导入缺失字段补零，来源系统固定回填

- 位置：`frontend/src/features/ai-hub/import/DataImportPanel.tsx:169`、`:184`；字段配置见 `importConfig.ts:73`～`:81`。
- 代码：`payload[field]?.trim() || '0'`；`payload.sourceSystem || 'CUSTOMER_WMS'`。
- 触发：上传文件未提供预留量、冻结量、安全库存、在途量或来源系统。这些字段在导入配置中允许不映射。
- 结果：向正式 `POST /api/v1/inventory/import/availability` 发送补出的数量零值和来源标识。“没有提供”因此变成“明确为零/明确来自 CUSTOMER_WMS”；若服务端接受，会进入正式事实链路。
- 归属：本次修改了同一导入逻辑的幂等与权限保护；上述补值在父提交已经存在，`git blame` 指向 `c0657b1`。
- 建议：先冻结各字段是否允许默认零及来源标识的契约。未经明确约定的事实缺失应阻止导入或返回缺失状态，来源取实际上传字段或授权连接器配置。`FULFILLABLE-V1` 是固定公式版本，不能仅因是常量就判为测试数据。

### FD-02 / P1：产品单位缺失自动变成“件”，可随新订单提交

- 位置：`frontend/src/features/sales/model/salesInventoryOptions.ts:24`、`:55`；消费位置 `frontend/src/App.tsx:2032`；提交位置 `frontend/src/features/sales/model/quickSalesOrder.ts:49`、`:73`。
- 代码：`unit === 'PCS' ? '件' : unit || '件'`。
- 触发：产品 API 没有提供单位。纯函数复现确认输出单位为“件”。
- 结果：新订单页面获得非空单位，`quickSalesOrderInput` 的“单位缺失”检查被绕过，构造的正式请求使用 `uom: '件'`。此外，PCS 显示为“件”后直接回传，混合了单位编码和显示名称。
- 归属：选项映射模块是既有依赖；本次新增订单严格校验和选择逻辑仍使用该映射结果。
- 建议：保留原始 `uom`，另设显示名称；缺单位显示“单位未提供”并阻止提交。单位编码转换必须有明确字典和接口约定。

### FD-03 / P1：工单被补成固定内部工序和“不良已处理”

- 位置：`frontend/src/features/production/model/formalProduction.ts:24`、`:27`；装载位置 `frontend/src/App.tsx:4824`；页面分支 `:4252`、`:4263`、`:4295`。
- 补值：`opId: "10"`、`opType: "内部"`、`isRework: false`、`ngHandled: true`；`operator` 直接使用工单创建人。
- 触发：正式工单进入现场作业看板，无需服务端返回工序、返工或不良处理事实。
- 结果：所有映射作业按内部加工路径展示，返工标识不会出现；即使不良数量大于零，`!j.ngHandled` 条件也不成立，返工按钮被隐藏。工单创建人也不能作为实际操作人的事实依据；当前卡片未直接展示该操作人字段。
- 归属：本次生产页面仍调用的既有映射依赖，并非本次新增测试工单数组。
- 建议：工序、加工方式、返工标识及不良处置状态使用相应正式事实；缺失时展示未知并明确限制操作。若看板只表达工单汇总，不应伪装为带真实工序和质量处置状态的作业卡。

### FD-04 / P2：MRP 建议单据量直接等于缺口，刷新时重置采购关联

- 位置：`frontend/src/App.tsx:4800`、`:4802`、`:4949`、`:4951`、`:5179`、`:5180`；展示 `:4168`，创建采购申请 `:5188` 后续处理。
- 补值/推导：`plannedQty = Number(shortage.shortageQty)`；`type: '采购件'`；`status: '待转采购'`。恢复行未从既有采购申请事实恢复 `purchaseRequestId`。
- 结果：批量规则已经显示“未提供”，但页面仍展示确定的“建议单据量”。同一会话创建采购申请后会回写真实申请 ID；重新恢复 MRP 行时没有该关联，按钮可能再次显示“采购申请”。
- 归属：本次修改 MRP 缺失状态时保留的旧推导。`:5179` 虽被本次改动覆盖，但父提交已有“缺口即建议量”表达。
- 边界：这不是随机测试数据。净缺口本身来自服务端；采购创建请求传的是任务、需求和物料引用，并未直接发送该 `plannedQty`。是否允许“建议量等于净缺口”需要产品/契约确认；重复创建能否产生重复单据取决于后端幂等规则，本轮未做写入验证。
- 建议：展示服务端采购建议及规则版本，或明确标成“净缺口参考量”；通过正式采购申请查询恢复状态及关联，不能以本地会话状态代替持久事实。

### FD-05 / P2：订单确认/发货弹窗仍将缺失金额和数量补为零

- 位置：`frontend/src/features/sales/components/SalesShipmentOrderEditModal.tsx:40`、`:46`、`:54`、`:80`、`:184`。
- 代码：金额格式化 `Number(value || 0)`；订单数量 `Number(order.qty || 0)`；行数量/单价缺失也参与补零计算，原价可以由这些值反算。
- 触发：历史订单、异常响应或页面映射缺少数量/单价/金额字段。
- 结果：只读业务事实可能显示为 `0` 或 `¥0.00`；原价可能显示由不完整数据计算的金额。当前本次新增的库存读取缺失状态已单独处理，不能因此认为整个弹窗都已保留缺失语义。
- 归属：本次修改过该文件，但上述零值回退是既有逻辑。
- 建议：既有订单的事实字段缺失显示 `-`/“数据待核实”，不反算；使用正式币种和金额快照。新建表单的默认折扣率 100%、优惠金额 0 应与历史事实缺失分开处理。

### FD-06 / P2：产品选项模型把“没有库存事实”变成可用量 0

- 位置：`frontend/src/features/sales/model/salesInventoryOptions.ts:38`、`:57`；引用 `frontend/src/App.tsx:3089`，报价弹窗展示取值 `:2020`。
- 触发：存在已启用、已关联仓库的产品，但库存事实数组为空或未包含该产品。
- 结果：纯函数复现得到 `availQty: 0`，丢失“尚未获取/没有此事实”的区别。报价模式消费 `line.available`，可将该补值显示为确定库存。
- 归属：既有依赖，非本次新增测试记录。
- 重要边界：当前快速开单的订单模式另行调用 `inventoryApi.getAvailability`，显示取 `orderAvailability`；缺失或失败置为 `null`。不能把选项模型的补零直接认定为快速开单当前显示假库存。本项也不代表正式报价保存已经开放。
- 建议：选项的可用量允许为空并携带来源状态；所有消费处使用明确的库存查询结果，缺失不能转零。
