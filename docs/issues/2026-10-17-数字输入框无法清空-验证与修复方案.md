# FE-NUM-001：数字输入框无法清空

- 日期：2026-10-17。
- 状态：已验证，方案待实施；本次仅调查、记录 issue 和设计方案。
- 优先级：P1，影响基础录入体验；目前可通过全选替换绕过，不判为所有业务均无法提交。
- 范围：前端数字输入及其草稿、校验、展示逻辑。不修改业务代码、后端、数据库或接口契约。
- 检查基线：Git `d566d1e`，结合检查时工作区的源码和正在运行的真实页面。

## 1. 问题结论

用户反馈的问题存在，但不能概括为“所有数字输入框默认都是 0、只能在 0 后追加”：

1. Playwright 实际操作 12 个字段，11 个无法保持空值；其中 10 个清空后补回 `0`，订单设置的触发阈值补回 `1`。供应商平均交期可以保持空值。
2. 初始值既有 `0`，也有 `1`、`100`、`10`、`7` 和空值。仓库容量、触发阈值最初为空，输入后再删除才触发问题。
3. 全选后直接输入 `12` 可以替换原值。直接删除无法清空属于缺陷，不能据此判断完全无法录入新数值。
4. 复现期间输入节点保持连接且焦点稳定，本问题不属于此前的焦点跳走或输入框重新挂载问题。
5. 浏览器内存、localStorage 或后端默认值不是本次已复现问题的直接原因；前端输入事件会立即把空字符串转换为数字并重新渲染。

### 3.2 相关风险：零值被显示为空

[App.tsx:3361](../../frontend/src/App.tsx#L3361) 的 `Prod_RecordModal` 和 [App.tsx:5389](../../frontend/src/App.tsx#L5389) 的 `Inv_RecordModal`，数字草稿输入时转 `Number`，展示时却使用 `draft[field.key] || ''`。数值 `0` 会显示为空，不能与“删除后补回 0”混为同一表现。

这两处列为源码发现的相关风险，需在实施前确认当前业务入口、字段是否允许编辑、是否仍在使用，再决定修改范围。不能借修复输入行为开放库存数量直接编辑能力，也不能恢复未开放的业务入口。销售通用表单也有 `|| ''` 写法，但其输入更新保存原始字符串，应单独检查初始值为数字 0 的回显，不能一概归为本缺陷。

### 3.3 对照和不应批量改动的范围

- 供应商交期 [App.tsx:7255](../../frontend/src/App.tsx#L7255) 已显式保留空字符串，本次页面验证可清空。
- [ProductionReportModal.tsx:29](../../frontend/src/features/production/components/ProductionReportModal.tsx#L29)、[PaymentAllocationModal.tsx:78](../../frontend/src/features/finance/components/PaymentAllocationModal.tsx#L78)、[PurchaseReceiptModal.tsx:44](../../frontend/src/features/procurement/components/PurchaseReceiptModal.tsx#L44) 的输入更新保存字符串，未发现本次输入时空值转 0 的写法；仅作源码对照，不代表其计算和提交校验已全部通过验收。
- 生产计划数量、BOM 用量/损耗率/最小起订量、工艺时间等已有保存字符串的输入路径，不应只因 `type="number"` 就批量改写。
- 本次发货数量在 [App.tsx:5762](../../frontend/src/App.tsx#L5762) 已有显式空值处理；非空值存在即时限幅，属于需另行核对的交互规则，不能直接标记为无法清空。
- 平台配置按草稿字符串处理；分页选择器、范围滑块、只读指标不属于本次数值文本录入问题。手机号、验证码、工序编码等标识值不得当作可计算数量统一转换。

## 4. 拟议修复方案（未实施）

### 4.1 编辑草稿与业务数值分离

1. 可编辑数字草稿统一保存输入原始字符串；读取接口数值和初始化默认值时转为对应显示字符串，保留真实零值。显示默认值与提交语义分开定义。
2. 允许用户通过 Backspace、Delete、全选删除保持 `''`，也允许直接替换数字。`onChange` 和 `onBlur` 均不擅自补 0、补 1 或按范围截断。
3. 本次不把所有初始值改为空。已有业务默认值 0、数量 1、折扣率 100 等先沿用；无正式配置的字段继续保持未配置状态，不伪造默认值。
4. 十进制输入需要支持编辑中的 `0.`、`1.` 等中间状态。若原生 `type="number"` 无法稳定保留这些状态，相关十进制字段采用字符串输入配合 `inputMode="decimal"`；整数控件的最终选型在兼容验证后确定。键盘类型不能替代校验。
5. 错误提示和保存失败不得重置用户草稿。只读、锁定和权限限制保持原有规则。

### 4.2 校验、计算与请求组装

1. 提交前先区分“空值”和“实际为 0”，再校验格式、精度、范围及跨字段关系。禁止用 `Number('')`、`parseInt(value) || 0` 把缺失值当有效零值。
2. 必填项空值显示字段错误并阻止请求；选填项清空后采用省略、`null` 或其他值，必须以该字段既有契约为准。契约未明确时列为待确认，不统一补 0，也不借本次设计更改后端。
3. 金额和数量按各字段已有接口类型及精度组装。既有十进制字符串契约继续传字符串；仅整数且请求要求数值的字段在通过校验后转换，并校验安全整数范围。
4. 可复用 [decimal.ts](../../frontend/src/shared/decimal.ts) 和 [commandValidation.ts](../../frontend/src/shared/commandValidation.ts) 的适用校验，不能把其中“非负、最多 6 位小数”推广为所有金额、数量、比例和整数的统一业务标准。
5. 草稿不完整或非法时，依赖它的金额、比例、差额等预览应明确为待计算，例如显示 `—`；不得伪装成有效零值。实施时需同时审查销售 `subtotal/total` 等 `Number(value || 0)` 计算，不能只替换输入事件。
6. 质检输入未形成有效数值时暂停由该字段驱动的联动覆盖，不清零其他字段；显示待校验状态。有效输入仍按既有良品/不良、报废/返修规则计算，最终提交继续执行数量守恒和范围校验。
7. 是否抽取共享输入组件或草稿工具，以实际重复程度决定。基础输入仅负责保存编辑值和展示错误，业务的精度、上下限、权限及数量守恒仍由各表单负责。

## 5. 后续验收标准

1. 初始为 0 的输入框，可用 Backspace、Delete 和全选删除清空，失焦后不会自动恢复 0；初始为 1、100 等同理。
2. 清空后输入 `7` 显示 `7`；选中原值后输入 `12` 显示 `12`，不被迫保留前导 0。用户主动输入 `07` 的规范化不得打断编辑，提交时按字段规则处理。
3. 字段允许 0 时，输入或回显 0 必须显示为 `0`；字段不允许 0 时显示校验错误，不自动改为 1。
4. 十进制逐字输入、粘贴、小数点中间态、精度边界均可验证；整数拒绝非整数，且不过早截断小数、负号或其他非法输入为有效业务值。
5. 必填空值、超范围、超精度和非法数值不发送业务请求；选填空值按已确认的字段契约处理。
6. 草稿无效时不展示误导性的确定金额或数量，不误改关联字段；草稿有效后的计算与修复前业务规则一致。
7. 保存成功请求类型正确且重开可回显；保存失败草稿和字段错误可见，焦点与连续输入稳定。
8. 回归覆盖新建、编辑、重复行、增删行、复制/粘贴、桌面键盘和移动数字键盘。测试仅修复相关行为，不新增未授权的写入能力。
