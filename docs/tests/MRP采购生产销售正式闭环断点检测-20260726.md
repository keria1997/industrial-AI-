# MRP—采购—生产—销售正式闭环断点检测报告

> 2026-07-27 更新：本报告记录的是修复前事实。原 P0 断点已按 Reference 范围关闭，复测结果见 `docs/tests/MRP采购生产销售正式闭环修复复测-20260727.md`。

## 1. 检测结论

- 检测日期：2026-07-26
- 目标链路：MRP -> 采购申请 -> 采购订单 -> 采购入库 -> 物料齐套 -> 生产入库 -> 库存再校验 -> 销售出库
- 结论：未形成正式闭环。
- 主要断点：`MRP -> PR/PO -> 采购入库 -> 物料齐套` 尚无正式后端业务链路；当前页面通过 React 共享状态和固定演示单号推进。
- 已实现边界：销售缺货生产需求、Reference MRP/APS、生产完工事件、成品库存事实推进、发货任务重校验、销售出库已有后端参考闭环，但当前生产主页面未完整接入该正式执行链路。

## 3. 未闭环原因

### 3.1 交付范围主动排除了采购闭环

`docs/usecase.md` 当前首期口径明确采用“物料已齐套试点”，不含自动 PR/PO，也不含采购入库；采购 `UC-040~042` 不属于首期退出条件。`docs/API接口文档.md` 也把采购入库列为库存后续能力，并注明采购域需要 ERP/SRM 接口。

因此目标 PRD 包含采购链路，但当前正式开发基线没有把采购纳入交付范围。这是范围缺口，不是已经实现后偶发失败。

### 3.2 Reference MRP 不会生成真实缺料结果

`server/src/service.ts` 的 Reference MRP 将 `materialShortages` 固定为空数组，并直接返回 `canProceedToAps: true`。它能证明需求、任务和结果持久化，但不会根据 BOM、物料库存、在途采购、预留和安全库存计算缺料，也不会生成 BUY 类型计划订单或采购建议。

数据库迁移虽然存在 `prod_plan_order` 和 `prod_purchase_suggestion_link` 表，但当前服务和测试没有读写这些表，属于仅有结构、没有可执行业务能力。

### 3.3 采购模块仍是前端原型

当前采购数据来自 `src/App.tsx` 中的常量 `proc_prData`、`proc_poData` 和临时 `linkedPrRow`、`linkedPoRow`。审批、转 PO、登记送货最终调用的是 `onBusinessFlowAction`，只改变根组件中的 `businessFlow.currentStep` 并显示成功提示。

不存在以下正式能力：

- 采购申请、审批记录和职责分离；
- 采购订单、订单行、供应商承诺、到货计划；
- 幂等键、乐观锁、租户过滤、审计、状态历史和 Outbox；
- MRP 结果、PR 行、PO 行、收货行之间的稳定 ID 映射。

### 3.4 采购入库没有形成权威库存事实

前端到达 `materialInbound` 后只在库存组件中插入 `IN-LINK-MAT-001`，并修改 `stockData` 数组。该动作没有调用正式库存 API，也不会产生采购收货、质检、库存事务、物料可用量版本或 Inbox/Outbox 事件。

因此生产齐套服务无法证明 RM201 已经到货并可用，也无法追踪采购入库数量是否覆盖某个 MRP 缺口。

### 3.5 当前生产入口没有接完正式执行链路

生产需求校验、审批和 Reference MRP 已接正式 API；但 `handleIssueMrp`、齐套检查、工单下达和多数车间动作仍更新本地状态。正式 `ProductionOperations` 页面保留在代码中但未挂载，且根据入口保护要求不能直接替换当前 `LegacyProductionManagement`。

所以即使前端显示“物料齐套、生产中、成品已入库”，也不一定产生正式工单、FQC、Completion、库存事务和完工事件。

### 3.6 正式重校验依赖的关联信息没有从采购链传递

后端完工重校验要求：

- 正式生产完工事件；
- 目标仓库、成品 ID、数量和单位；
- 新库存事实版本；
- `allocations[]` 中的生产需求 ID；
- 发货任务行已保存相同 `productionDemandId`。

前端共享流程状态没有提供完整的正式事件和分配关系，所以无法把关联发货任务可靠推进到 `RECHECKING`。页面按钮可以把步骤推进到“销售出库”，但这不等于正式库存任务已经重校验和预留成功。

## 4. 为什么现有测试没有覆盖这个缺口

现有 `server/test/fulfillment-api.test.ts` 覆盖的是物料已齐套路径：Reference MRP 断言 `materialShortages: []`，随后直接执行 APS、创建 `kittingStatus: READY` 的工单、报工、FQC 和完工。

2026-07-26 本次复跑结果：

- `server/test/fulfillment-api.test.ts`：3 条通过；
- `server/test/production-fulfillment-worker.test.ts`：1 条通过；
- 合计 4 条通过。

这些结果证明“生产完工 -> 成品库存事实 -> 重校验 -> 销售出库”参考链路可执行，但没有任何用例创建正式 PR、PO、采购收货或物料库存事实，因此不能证明采购参与的完整闭环。

## 5. 正式闭环所需最小补齐顺序

1. 实现采购域 PR、审批、PO、到货/收货聚合及正式 API、仓储、状态历史、审计和 Outbox。
2. 让 MRP 基于正式 BOM 和物料可用量输出 `materialShortages`、MAKE/BUY 计划订单，并用稳定 ID 转换为 PR。
3. 实现采购入库、来料质检、库存事务和物料可用量事实；PO 行、收货行、库存流水保持可追溯。
4. 实现正式齐套计算与物料预留，只有缺料全部覆盖后才允许工单下达。
5. 在保留 `LegacyProductionManagement` 主入口的前提下，局部接入正式 APS、工单、报工、FQC 和完工 API。
6. 由正式完工事件推进成品库存事实和关联发货任务 `RECHECKING`，再执行正式预留和销售出库。
7. 新增一条不能绕过采购的端到端测试：初始 RM201 不足，必须经过 PR、PO、采购入库和齐套后才允许创建/下达工单，并最终把原销售订单推进为 `SHIPPED`。
