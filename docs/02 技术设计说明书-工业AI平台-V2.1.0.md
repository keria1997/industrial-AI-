# 技术设计说明书 - 工业AI平台 V2.1.0

> 文档版本：`TD-DEVBASE-R20261015`
> 依据：`V2.1.0-PRD-DEVBASE-R20261015`（第 17 章开发就绪实施基线）
> 约束：本设计文档定义开发蓝图，不修改业务代码。

## 1. 文档目的与范围

### 1.1 目的

本文档将 PRD 的业务需求转换为可实施的技术方案，明确前后端架构、模块边界、数据库设计、API 契约、事件流、权限模型和部署策略，使开发团队能够按模块并行开发。

### 1.2 范围

本设计覆盖 PRD 第 17 章定义的 P0 交付范围：

- 销售、库存、生产、采购、财务：平台内最小完整闭环。
- 工作台、身份认证、权限治理、消息投影、审计。
- 平台内 AR/AP、收付款核销、冲销、销售完成关闭。

不在本设计范围：外部 ERP/SRM/MES/WMS/财务系统对接、AI 生产化、移动端、真实大模型、银行直连。

### 1.3 术语与缩略词

| 术语 | 定义 |
| --- | --- |
| Outbox | 同事务写入的事件发件箱表，由 Worker 异步投递 |
| Inbox | 消费者侧事件去重表，防止重复消费 |
| Correlation ID | 贯穿同一业务链路的追踪标识 |
| 幂等键 | 客户端传入的唯一操作标识，重复请求返回首次结果 |
| RLS | PostgreSQL Row-Level Security，租户级数据隔离 |

### 2.3 架构原则

1. **租户隔离**：所有业务表启用 PostgreSQL RLS，会话令牌携带 `tenantId`，数据库连接通过 `SET app.tenant_id` 注入租户上下文。
2. **服务端权威**：业务状态、数量、金额以服务端数据库事实为唯一权威，前端仅为投影展示。
3. **事件驱动**：跨模块数据同步通过 Outbox → Worker → 目标模块 API/Inbox 完成，禁止跨模块直接 UPDATE 对方表。
4. **幂等安全**：所有写操作携带 `idempotencyKey`，重复请求返回首次结果，结果未知时保持处理中。
5. **审计全覆盖**：所有写操作记录操作者、时间、前后值、原因、Correlation ID 和 Trace ID。
6. **禁用外部**：外部系统接口只预留契约和配置位，不得用模拟数据推进业务状态。

### 3.2 状态管理策略

本项目不引入 Redux/Zustand 等外部状态库，采用 React 内置状态管理：

| 状态类型 | 管理方式 | 说明 |
| --- | --- | --- |
| 会话与权限 | `AppRuntimeProvider` + Context | 全局令牌、当前租户、权限集合、角色列表 |
| 页面数据 | 组件局部 `useState` + `useEffect` | 加载 API 数据，卸载清理 |
| 表单状态 | 受控组件 | 提交前校验，失败保留输入 |

| 跨组件通知 | 自定义事件（`window.dispatchEvent`） | 仅用于消息提醒等非关键通知 |

### 3.3 路由与权限

```
URL 结构: ?module={moduleId}&tab={tabId}&focus={docId}
```

每个模块在 `moduleRegistry.ts` 中注册：

```typescript
interface ModuleRegistration {
  id: string;                    // 如 'sales', 'inventory', 'workbench'
  label: string;                 // 导航显示名
  icon: LucideIcon;              // Lucide 图标
  requiredPermission: string;    // 服务端权限码，如 'sales.order.read'
  defaultTab: string;            // 首页页签 ID
  tabs: TabRegistration[];       // 页签列表
}
```

权限守卫流程：

1. 前端从 `AppRuntimeProvider` 读取当前用户权限集合。
2. 无权限的模块在侧栏隐藏；URL 直达时重定向到工作台。
3. 后端每次请求从签名会话重算权限，前端隐藏不等于服务端授权。
4. 权限变更（撤权/授权发布）后，下一次 API 请求立即生效，前端在响应 403 时刷新权限集合并清理过期 UI。

### 4.2 分层架构

每个业务模块遵循三层分离：

```
Controller (REST API)
    ↓ 调用
Service (业务逻辑 + 状态机 + 校验)
    ↓ 调用
Store (数据访问接口)
    ↓ 实现
JdbcStore (PostgreSQL JDBC + RLS)
    ↓ 使用
HikariCP DataSource
    ↓ 连接
PostgreSQL (RLS + 事务)
```

### 4.3 请求上下文

每个请求经过 `RequestContextService` 解析并注入以下上下文：

```java
public class RequestContext {
    private String tenantId;
    private String accountId;
    private String actorName;
    private Set<String> permissions;   // 服务端 IAM 计算
    private String correlationId;
    private String traceId;
    private String idempotencyKey;    // 从请求头 X-Idempotency-Key 提取
}
```

`RequestContext` 通过 Spring `RequestScope` Bean 注入到 Service 和 Store 层。JDBC 连接在执行 SQL 前通过 `SET app.tenant_id = ?` 注入租户 ID，配合 PostgreSQL RLS 策略实现数据隔离。

### 4.4 事务与并发控制

| 场景 | 隔离级别 | 并发控制 | 说明 |
| --- | --- | --- | --- |
| 库存预留 | `READ COMMITTED` | `SELECT ... FOR UPDATE` | 原子锁定库存事实行，检查可用量后写入预留 |
| 出库过账 | `READ COMMITTED` | `SELECT ... FOR UPDATE` | 锁定预留行 + 库存事实，扣减现存和预留 |
| AR/AP 确权 | `READ COMMITTED` | 唯一索引 + `ON CONFLICT DO NOTHING` | 幂等键唯一，重复插入返回已有事实 |
| 核销 | `READ COMMITTED` | `SELECT ... FOR UPDATE` | 锁定 AR 行，校验余额后写入核销记录 |
| 状态机推进 | `READ COMMITTED` | 乐观锁 `version` 列 | `UPDATE ... WHERE version = ?`，失败返回 409 |
| 跨模块事件消费 | `READ COMMITTED` | Inbox 唯一约束 | 同一 `eventId` 只消费一次 |

**客户签收状态与销售订单完成状态关系：**

客户签收（`CustomerReceipt.receiptStatus`）和销售订单（`SalesOrder.overallStatus`）是独立实体和独立状态机。客户签收 `SIGNED` 是销售订单 `COMPLETED` 的前置条件之一，但不等于完成。销售订单 `COMPLETED` 需同时满足：全部行 `SHIPPED` + 签收 `SIGNED` + AR `SETTLED` + 无未关闭 RMA/争议。前端不得将签收状态直接映射为订单状态。

所有模块监控舱页面的统计卡片、AI 卡片和趋势图数据必须从对应的后端 API 聚合计算，不得使用硬编码值。

### 7.4 Outbox Worker 设计

每个模块域一个 Worker 实例：

```java
@Scheduled(fixedDelay = 1000)  // 每秒轮询
public void processPendingEvents() {
    List<EventOutbox> pending = outboxStore.findPending(50);
    for (EventOutbox event : pending) {
        try {
            deliver(event);
            outboxStore.markDelivered(event.getId());
        } catch (Exception e) {
            outboxStore.incrementRetry(event.getId());
            if (event.getRetryCount() >= event.getMaxRetries()) {
                outboxStore.markDeadLetter(event.getId());
            }
        }
    }
}
```

投递语义：至少一次（At-Least-Once）。消费方通过 Inbox 表去重。

### 10.3 原型缓存退役与回填防护（2026-10-17）

#### 10.4.1 产品默认仓库未接通：后端交接（2026-10-17）

PRD 7.5要求产品新增/编辑必须选择默认仓库，并在刷新、仓库详情中保持配置；当前只读降级是实现缺口，不代表该需求已交付。本轮真实页面读取4个仓库、7个产品，产品均未包含`defaultWarehouseId`。前端共用编辑器将仓库选择设为`locked`；产品创建client不提交该字段，当前映射从单仓库存事实推导归属，该推导不能用作默认仓库配置或保存依据。

后端需要先完成：

1. `POST /api/v1/inventory/products`接收必填`defaultWarehouseId`（仓库服务端ID），与产品其余字段在同一事务内持久化；当前`FulfillmentService.createMaster`未复制或保存该字段。
2. `PATCH /api/v1/inventory/products/{id}`允许更新`defaultWarehouseId`；当前`FulfillmentController.updateProduct`白名单不含该字段。沿用`If-Match`及现有幂等机制，不能忽略字段却返回成功。
3. 产品集合GET、详情GET、新建及编辑响应中的`product`统一返回真实`defaultWarehouseId`和最新`version`。历史记录未配置时明确返回`null`，不得用库存事实或第一个启用仓库代替。
4. 写入时按当前租户、用户仓库授权范围、启用状态及PRD分类兼容规则校验；缺失/无效值、越权、已停用、版本冲突按统一错误契约拒绝，不保存部分配置。仓库分类兼容矩阵若未冻结，需先确认，不由前端猜测。
5. 默认仓库变更只改变主数据配置，不搬移、增加或扣减库存；仓库删除引用检查必须包含该配置。

后端完成后，前端再将`defaultWarehouseId`加入DTO与POST/PATCH字段；解除锁定，仅允许选择API返回的授权启用仓库。列表、编辑回显直接使用该字段，保留未配置状态，不再从库存事实推导默认仓库。校验空选择、停用/越权、无可选仓库、失败保留草稿及保存后重新读取。验收须核对新建/修改→数据库配置→GET回读→列表/详情/重新打开弹窗一致，并确认原仓库存事实没有随配置变更。

本轮仅增加前端不可用原因说明和本交接条目，未解除禁用、未修改后端或数据库，不能将“已能选择并保存仓库”标记为完成。物料存在相同接口缺口，但本项交接以用户反馈的产品新增/编辑为范围。

### 10.6 前端业务动作整改与联调边界（2026-10-17）

本节补充现有实现约束，不削减 PRD 完整闭环 P0 范围。不修改后端代码；受控 API 回归通过不能视为数据库、事务、审计、职责分离的服务端验收通过。

1. **金额与数量命令**：表单金额/数量保留十进制字符串，使用精确十进制比较，禁止将未结余额自动当成本次金额。登记收付款调用现有 `POST /api/v1/finance/payments`，来源 ID、往来单位和币种必须来自正式单据；确认使用 `POST /finance/payments/{id}/confirm` 和服务端版本。登记成功只代表登记，不代表已核销、已开票或已生成凭证。收付款确认另设列表及确认入口；登记人与确认人分离，服务端仍为权威判定。
2. **未知结果**：新登记、复核、收货、质检和退货表单防止并发重复点击；网络异常、408、429、5xx 和缺少成功结果时保留输入、冻结原参数，重试复用同一幂等键。确定失败允许修正后提交。幂等键按具体命令/单据隔离，不跨单据复用。版本冲突不得本地递增版本或假定成功。
3. **采购分批执行**：本批实收不得大于 `orderedQty - receivedQty`，每批填写送货单号和实收数量。部分入库订单继续允许收货；送货不等于入库，按响应显示 `PENDING_INSPECTION` 或 `POSTED`。现有 IQC 契约仅支持整批 ACCEPTED/REJECTED；部分合格/不合格数量、证据及版本契约待补齐，不能认定完整 IQC 完成。退货申请成功不等于审批/出库，只有来源状态 APPROVED 且有权限才可办理。
4. **权限**：导航只依赖签名会话/权限复核返回的有效权限，不根据角色名称放行业务入口；空权限不授权销售或工作台。租户/令牌作用域变化先停止渲染旧业务内容；403 和发布授权触发 readiness 复核。相同作用域复核期间以遮罩阻止继续操作，保留表单；实际撤权后卸载受保护页面。复核失败关闭业务访问并提供重试。权限接口返回不变的权限集合时复用原集合，避免 403→复核→自动重读的立即循环。
5. **授权发布**：预览逐条展示权限码与旧/新效果。发布后重查权威快照获取实际版本，禁止前端 `version + 1`；发布成功触发当前会话权限刷新。服务端草稿保存、复核、历史版本和撤销缺少统一契约，仍是未完成的 P0 依赖，本页内存草稿不替代这些功能。
6. **工作台**：指标 `sections=metrics` 每300秒读取，待办/预警/动态 `sections=todos,alerts,activities` 每60秒读取；手动刷新分别重读。查询携带 search、KEY/ALL、todoLimit=5、activityLimit=10及服务端游标。页面不按客户端规则生成正式预警。缓存仅在内存，按租户、令牌、用户、角色、权限/范围版本、日期隔离；失败保留同作用域最近快照并显示异常，超过300秒标过期，超过1800秒指标值改为 `-`，超过5分钟未同步的事项禁用处理并标待核对。当前兼容原 flat DTO 与 PRD schemaVersion=1.1；字段缺失/未知版本明确报错，不伪造零。金额按币种/税口径分别展示，数量按工厂/单位分组。1.1 未提供总数时不以受限列表长度冒充聚合数量。多来源状态按 sources 显示，不把局部失败隐藏。
7. **分页及穿透**：AR/AP/成本和收付款按服务端 page/pageSize/total 请求；消息按服务端搜索、业务分类、分页和归档确认。客户/销售订单采用完整分页读取后搜索，已消除首100/200条截断，但仍未达到服务端条件查询/大数据量性能验收。采购现有集合接口未冻结分页参数，先校验 items 与 total 完整性，再分页展示；不完整时拒绝假装全量。工作台/消息按来源类型、稳定 ID 映射模块专属参数，不按按钮文字或显示单号猜测来源；无法识别来源时禁止跳转。财务来源直接按稳定 ID 查询；销售、采购、生产和出库页面匹配稳定 ID。快捷开单打开真实表单，报工进入正式执行页；缺少独立新增契约的手工入库/手工 PR 保持不可用。

4. **订单穿透**：使用源 `orderId` 写入销售订单 `focusOrder`，定位列表并允许查看详情；不以显示单号猜测ID，不在跳转时推进订单状态。没有订单读取权限时只显示文本。
5. **办理门槛**：查询已通不等于写入合规。当前RMA创建未核验原出库行/可退余量；审批缺职责分离；检验跳过在途/收货并要求全量实收；关闭仍按申请数量取负数构造红字金额。客户签收仍信任请求中的发货总量、未按订单/出库行核验唯一聚合和累计差额。前端保持办理入口受限，不能通过删减PRD状态机使之验收通过。
6. **验证边界**：真实脚本新增两页API/UI标识及数量/签收状态核对，SQL/API核对覆盖页面来源字段。44页仍是渲染冒烟；专用客户写入闭环不代表退货、签收、财务、生产等所有命令已验收。受控浏览器回归另测分页、失败/空集/重试、缺币种、缺数量、无权限和订单穿透；与真实数据库结果分别报告。
