# 技术设计说明书 - 工业AI平台 V2.1.0

> 文档版本：`TD-DEVBASE-R20261015`
> 依据：`V2.1.0-PRD-DEVBASE-R20261015`（第 17 章开发就绪实施基线）
> 约束：本设计文档定义开发蓝图，不修改业务代码。

## 1. 文档目的与范围

### 1.1 目的

本文档将 PRD 的业务需求转换为可实施的技术方案，明确前后端架构、模块边界、数据库设计、API 契约、事件流、权限模型和部署策略，使开发团队能够按模块并行开发。

### 1.2 范围

本设计覆盖 PRD 第 17 章定义的 P0 交付范围：

- 销售、库存、生产、采购、财务：平台内最小完整闭环。
- 工作台、身份认证、权限治理、消息投影、审计。
- 平台内 AR/AP、收付款核销、冲销、销售完成关闭。

不在本设计范围：外部 ERP/SRM/MES/WMS/财务系统对接、AI 生产化、移动端、真实大模型、银行直连。

### 1.3 术语与缩略词

| 术语 | 定义 |
| --- | --- |
| Outbox | 同事务写入的事件发件箱表，由 Worker 异步投递 |
| Inbox | 消费者侧事件去重表，防止重复消费 |
| Correlation ID | 贯穿同一业务链路的追踪标识 |
| 幂等键 | 客户端传入的唯一操作标识，重复请求返回首次结果 |
| RLS | PostgreSQL Row-Level Security，租户级数据隔离 |

### 2.3 架构原则

1. **租户隔离**：所有业务表启用 PostgreSQL RLS，会话令牌携带 `tenantId`，数据库连接通过 `SET app.tenant_id` 注入租户上下文。
2. **服务端权威**：业务状态、数量、金额以服务端数据库事实为唯一权威，前端仅为投影展示。
3. **事件驱动**：跨模块数据同步通过 Outbox → Worker → 目标模块 API/Inbox 完成，禁止跨模块直接 UPDATE 对方表。
4. **幂等安全**：所有写操作携带 `idempotencyKey`，重复请求返回首次结果，结果未知时保持处理中。
5. **审计全覆盖**：所有写操作记录操作者、时间、前后值、原因、Correlation ID 和 Trace ID。
6. **禁用外部**：外部系统接口只预留契约和配置位，不得用模拟数据推进业务状态。

### 3.2 状态管理策略

本项目不引入 Redux/Zustand 等外部状态库，采用 React 内置状态管理：

| 状态类型 | 管理方式 | 说明 |
| --- | --- | --- |
| 会话与权限 | `AppRuntimeProvider` + Context | 全局令牌、当前租户、权限集合、角色列表 |
| 页面数据 | 组件局部 `useState` + `useEffect` | 加载 API 数据，卸载清理 |
| 表单状态 | 受控组件 | 提交前校验，失败保留输入 |

| 跨组件通知 | 自定义事件（`window.dispatchEvent`） | 仅用于消息提醒等非关键通知 |

### 3.3 路由与权限

```
URL 结构: ?module={moduleId}&tab={tabId}&focus={docId}
```

每个模块在 `moduleRegistry.ts` 中注册：

```typescript
interface ModuleRegistration {
  id: string;                    // 如 'sales', 'inventory', 'workbench'
  label: string;                 // 导航显示名
  icon: LucideIcon;              // Lucide 图标
  requiredPermission: string;    // 服务端权限码，如 'sales.order.read'
  defaultTab: string;            // 首页页签 ID
  tabs: TabRegistration[];       // 页签列表
}
```

权限守卫流程：

1. 前端从 `AppRuntimeProvider` 读取当前用户权限集合。
2. 无权限的模块在侧栏隐藏；URL 直达时重定向到工作台。
3. 后端每次请求从签名会话重算权限，前端隐藏不等于服务端授权。
4. 权限变更（撤权/授权发布）后，下一次 API 请求立即生效，前端在响应 403 时刷新权限集合并清理过期 UI。

### 4.2 分层架构

每个业务模块遵循三层分离：

```
Controller (REST API)
    ↓ 调用
Service (业务逻辑 + 状态机 + 校验)
    ↓ 调用
Store (数据访问接口)
    ↓ 实现
JdbcStore (PostgreSQL JDBC + RLS)
    ↓ 使用
HikariCP DataSource
    ↓ 连接
PostgreSQL (RLS + 事务)
```

### 4.3 请求上下文

每个请求经过 `RequestContextService` 解析并注入以下上下文：

```java
public class RequestContext {
    private String tenantId;
    private String accountId;
    private String actorName;
    private Set<String> permissions;   // 服务端 IAM 计算
    private String correlationId;
    private String traceId;
    private String idempotencyKey;    // 从请求头 X-Idempotency-Key 提取
}
```

`RequestContext` 通过 Spring `RequestScope` Bean 注入到 Service 和 Store 层。JDBC 连接在执行 SQL 前通过 `SET app.tenant_id = ?` 注入租户 ID，配合 PostgreSQL RLS 策略实现数据隔离。

### 4.4 事务与并发控制

| 场景 | 隔离级别 | 并发控制 | 说明 |
| --- | --- | --- | --- |
| 库存预留 | `READ COMMITTED` | `SELECT ... FOR UPDATE` | 原子锁定库存事实行，检查可用量后写入预留 |
| 出库过账 | `READ COMMITTED` | `SELECT ... FOR UPDATE` | 锁定预留行 + 库存事实，扣减现存和预留 |
| AR/AP 确权 | `READ COMMITTED` | 唯一索引 + `ON CONFLICT DO NOTHING` | 幂等键唯一，重复插入返回已有事实 |
| 核销 | `READ COMMITTED` | `SELECT ... FOR UPDATE` | 锁定 AR 行，校验余额后写入核销记录 |
| 状态机推进 | `READ COMMITTED` | 乐观锁 `version` 列 | `UPDATE ... WHERE version = ?`，失败返回 409 |
| 跨模块事件消费 | `READ COMMITTED` | Inbox 唯一约束 | 同一 `eventId` 只消费一次 |

**客户签收状态与销售订单完成状态关系：**

客户签收（`CustomerReceipt.receiptStatus`）和销售订单（`SalesOrder.overallStatus`）是独立实体和独立状态机。客户签收 `SIGNED` 是销售订单 `COMPLETED` 的前置条件之一，但不等于完成。销售订单 `COMPLETED` 需同时满足：全部行 `SHIPPED` + 签收 `SIGNED` + AR `SETTLED` + 无未关闭 RMA/争议。前端不得将签收状态直接映射为订单状态。

所有模块监控舱页面的统计卡片、AI 卡片和趋势图数据必须从对应的后端 API 聚合计算，不得使用硬编码值。

## 7. 事件设计

### 7.1 事件流架构

```
┌──────────┐     同事务      ┌──────────┐     Worker 轮询    ┌──────────────┐
│ 业务写入  │ ───────────→  │ event_   │ ────────────────→  │ 目标模块      │
│ (Service)│               │ outbox   │                    │ API / Inbox  │
└──────────┘               └──────────┘                     └──────────────┘
                                                                 │
                                                                 ↓ 去重后处理
                                                           ┌──────────────┐
                                                           │ event_inbox  │
                                                           └──────────────┘
```

### 7.2 首批事件目录

| 来源模块 | 事件类型 | 触发时机 | 消费方 |
| --- | --- | --- | --- |
| 销售 | `sales.order.confirmed` | 确认内容成功 | 库存（创建仓库任务） |
| 销售 | `sales.order.ship_requested` | 发货申请成功 | 库存 |
| 库存 | `inventory.reservation.created` | 预留成功 | 销售（更新发货状态） |
| 库存 | `inventory.shortage.detected` | 库存不足 | 生产（创建需求） |
| 库存 | `inventory.outbound.posted` | 出库过账成功 | 销售 + 财务（AR 确权） |
| 生产 | `production.mrp.succeeded` | MRP 成功 | 采购（创建 PR） |
| 生产 | `production.completion.posted` | 完工入库成功 | 库存 + 消息 |
| 采购 | `procurement.receipt.posted` | 收货入库成功 | 库存 + 财务（AP 确权） |
| 财务 | `finance.ar.settled` | AR 结算完成 | 销售（更新完成条件） |
| 财务 | `finance.sales_order.completed` | 销售完成关闭 | 消息 + 工作台 |

### 7.4 Outbox Worker 设计

每个模块域一个 Worker 实例：

```java
@Scheduled(fixedDelay = 1000)  // 每秒轮询
public void processPendingEvents() {
    List<EventOutbox> pending = outboxStore.findPending(50);
    for (EventOutbox event : pending) {
        try {
            deliver(event);
            outboxStore.markDelivered(event.getId());
        } catch (Exception e) {
            outboxStore.incrementRetry(event.getId());
            if (event.getRetryCount() >= event.getMaxRetries()) {
                outboxStore.markDeadLetter(event.getId());
            }
        }
    }
}
```

投递语义：至少一次（At-Least-Once）。消费方通过 Inbox 表去重。

## 8. 权限设计

### 8.1 权限模型

```
账号 (Account)
    ↓ 绑定
员工 (Employee)
    ↓ 分配
角色 (Role)
    ↓ 授权
资源动作 (ResourceAction)
    ↓ 约束
数据范围 (DataScope)
```

### 8.2 权限码格式

统一格式：`{module}.{resource}.{action}`

示例：`sales.order.approve`、`inventory.outbound.execute`、`finance.payment.confirm`

### 8.3 数据范围

| 范围类型 | 说明 |
| --- | --- |
| `ALL_TENANT` | 租户全量（老板/租户所有者） |
| `OWN_DEPARTMENT` | 本部门 |
| `OWN_DATA` | 仅本人创建 |
| `CUSTOM_FACTORY` | 指定工厂 |
| `CUSTOM_WAREHOUSE` | 指定仓库 |
| `CUSTOM_CUSTOMER` | 指定客户 |

多角色账号取权限并集、数据范围并集；deny 规则优先于 allow。

### 8.4 授权版本发布

权限草稿保存后不影响线上；执行"发布"时原子递增 `authorization_version` 并记录审计。下次请求时服务端从新版本计算权限。撤销权限立即生效，不需要等待令牌过期。

### 10.3 原型缓存退役与回填防护（2026-10-17）

依据 PRD 7.4.99.1，在前端入口首次渲染前执行原型缓存清理，并安装退役键读写防护。清理采用业务命名空间匹配，覆盖 `industrial-ai-sales`、`industrial-ai-inventory-*`、`industrial-ai-production-legacy`、`industrial-ai-production-v*`、`industrial-ai-platform-v*` 等历史版本，不绑定单一版本号或租户。分别处理 localStorage 与 sessionStorage；单个存储不可用时不得中断应用启动。

不清理 `industrial-ai-session:v2`、`industrial-ai-runtime:tenant:v1:*`、`industrial-ai:outbound-command:v1:*` 以及正式生产记录 ID 索引。ID 索引仅用于重新读取 API，不得直接渲染为正式记录。禁止通过 `clear()` 删除整个站点存储。

运行时读取退役业务键返回空值，写入被拒绝并提供“请通过业务接口保存”的错误；删除旧键允许执行。销售、生产与平台页面取消自动保存原型快照，库存主数据加载异常不生成种子或参考价格。测试示例移至测试夹具，运行时代码不得引用测试夹具。

业务列表默认空集合；指标未知显示“-”，真实零值为 0。AI 卡片、趋势图沿用既定空态，框架保持可见。平台快照加载成功后使用完整服务端快照，失败保留空态与错误提示。尚无 API 的旧写入入口显示未保存，不得先更新本地列表或提示成功。

验证应覆盖：历史版本及多租户清除、重复启动、阻止回写、合法会话保留、存储访问异常、空/失败 API 页面状态与正式 API 数据仍可展示。此变更不涉及后端实现、数据库记录清理或接口迁移。

### 10.4 正式接口替代原型读写（2026-10-17）

- 删除页面对退役 Storage 业务桥接的依赖，导航/日期/建议数量等纯函数保留；业务查询不得再合并原型列表。读失败和租户切换均清空旧事实，异步响应按请求代次或 effect 清理标记隔离。

- 平台保存遵循实际 Controller 路径：集合 POST 新建、`PUT /{id}` 编辑、DELETE 删除，应用能力使用 POST `/capabilities`。快照将 `auditLogs` 规范为前端 `audits`。保存后重查快照，不自行追加假审计。多个实体改变不能伪装一次原子提交；无对应端点的租户资料、适配同步动作明确阻断。

- 启动、窗口获得焦点及其他标签页 Storage 变更时扫描清理退役业务键；Storage 防护重复安装保持幂等。保留正式登录会话、租户偏好、出库幂等命令及服务端 ID 索引，禁止全库 `clear()`。
