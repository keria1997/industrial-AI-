# 首期数据库设计：销售—库存—生产—发货

## 1. 文档信息

| 项目 | 内容 |
| --- | --- |
| 设计版本 | `FULFILLMENT-DB-DESIGN-20260726-01` |
| 业务基线 | `DELIVERY-BASELINE-20260726-02` |
| API 草案 | `server/docs/openapi-sales-inventory-draft.yaml` `0.2.0-development-baseline` |
| 数据库 | PostgreSQL 15+ |
| 设计状态 | 已批准作为开发基线；允许生成正式迁移，客户生产 DBA 仍须在上线前复核 |
| 首期终点 | 销售订单 `SHIPPED` |

本文把已冻结的字段模型、状态机、权限、幂等和事件语义转换为可实施数据库设计。本文不代表销售订单、库存预留或销售出库后端已经实现，也不替代当前已执行的 `001_production_p0.sql`、`002_sales_production_link.sql`。

## 2. 设计原则

1. 销售、库存、生产各自拥有数据；跨域只保存稳定来源 ID 和不可变快照，不建立跨域外键，不跨域直接更新表。
2. 每个业务表显式包含 `tenant_id`，应用查询必须带租户条件，数据库同时启用并强制 RLS。
3. 聚合写入、状态历史、审计和 Outbox 在同一本地事务完成；消费方先写 Inbox，再在同一事务更新本域投影。
4. 聚合使用 UUID；平台主数据、客户、产品、员工、组织、仓库和工厂使用不透明 `text` 稳定 ID。
5. 数量使用 `numeric(18,6)`，金额使用 `numeric(20,6)`，API 使用十进制字符串；业务计算不得使用浮点数。
6. 所有可变聚合使用 `version bigint` 乐观锁。更新条件必须包含 `tenant_id + id + version`，成功后 `version = version + 1`。
7. JSONB 只保存地址、外部回包、批次分配、前后快照和证据；状态、数量、来源、时间等查询字段必须结构化。
8. 已过账库存流水、审批动作、状态历史、审计和事件不可修改或删除；纠错新增反向事实或补偿记录。
9. 首期采用扩展后收缩迁移。正式事实产生后不得通过回滚删除订单、预留、流水或消息记录。

## 3. 命名与公共字段

### 3.1 表前缀

| 前缀 | 所属边界 | 示例 |
| --- | --- | --- |
| `sales_` | 销售域 | `sales_order`、`sales_shipment_request` |
| `inv_` | 库存域 | `inv_availability_projection`、`inv_sales_outbound` |
| `integration_` | 跨域可靠传输与补偿 | `integration_event_outbox` |
| `shared_` | 写命令治理和审计 | `shared_idempotency_record` |

新表使用单数名称，避免与现有 `prod_*` 混用。生产域现有表本期不重命名。

### 3.2 聚合公共字段

所有聚合根至少包含：

```text
id uuid primary key default gen_random_uuid()
tenant_id text not null
version bigint not null default 1 check (version >= 1)
correlation_id uuid not null
created_by text not null
created_at timestamptz not null default now()
updated_by text
updated_at timestamptz not null default now()
unique (tenant_id, id)
```

子表也必须保存 `tenant_id`，并通过 `(tenant_id, parent_id)` 复合外键引用同域父表，防止错误跨租户关联。`updated_at` 由触发器维护，`version` 只由应用层在成功执行命令时递增，普通触发器不得因无业务变化自动提升版本。

## 4. 销售域表

### 4.1 `sales_order`

销售订单聚合根，保存客户、履约配置、审批策略快照和三轴状态。

| 字段 | 类型 | 约束/说明 |
| --- | --- | --- |
| `order_no` | `varchar(50)` | 非空，`unique(tenant_id, order_no)` |
| `customer_id` | `text` | 非空，稳定主数据 ID |
| `customer_name_snapshot` | `varchar(200)` | 非空，不随主数据覆盖 |
| `owner_employee_id`、`owner_org_id` | `text` | 非空，权限数据范围锚点 |
| `fulfillment_warehouse_id` | `text` | 非空，首期单订单单履约仓 |
| `factory_resource_id` | `text` | 非空，缺货生产目标工厂 |
| `currency` | `char(3)` | 非空，检查大写三字符 |
| `total_amount` | `numeric(20,6)` | 非空且 `>= 0` |
| `order_date` | `date` | 非空 |
| `requested_delivery_date` | `date` | 非空且 `>= order_date` |
| `allow_partial_shipment` | `boolean` | 非空 |
| `review_required` | `boolean` | 非空，创建时策略快照 |
| `review_policy_version` | `varchar(40)` | 非空 |
| `overall_status` | `varchar(32)` | `PENDING_CONFIRMATION/CONFIRMED/REPLENISHING/PARTIALLY_SHIPPED/SHIPPED/CANCELED` |
| `review_status` | `varchar(24)` | `NOT_REQUIRED/PENDING/APPROVED/REJECTED/RETURNED/CANCELED` |
| `shipment_status` | `varchar(24)` | `NOT_REQUESTED/REQUESTED/PARTIALLY_SHIPPED/SHIPPED` |
| `source_quote_id` | `uuid` | 可空，仅保存销售域报价来源 |
| `source_quote_revision` | `bigint` | 与来源报价同时为空或非空 |
| `recipient_name` | `varchar(100)` | 非空 |
| `recipient_phone_ciphertext`、`recipient_phone_key_id` | `text/varchar(100)` | 非空，应用层信封加密并保存密钥版本；不得保存明文旁路字段 |
| `delivery_address` | `jsonb` | 非空，按 OpenAPI `Address` 校验 |
| `cancel_reason`、`canceled_by`、`canceled_at` | 文本/文本/时间 | `CANCELED` 时全部非空，其他状态为空 |

核心约束：`SHIPPED` 订单的 `shipment_status` 必须为 `SHIPPED`；`CANCELED` 的 `review_status` 必须为 `CANCELED`；这些约束不能替代应用层完整状态机。

核心索引：

```sql
create index ... on sales_order (tenant_id, overall_status, updated_at desc);
create index ... on sales_order (tenant_id, owner_org_id, owner_employee_id, updated_at desc);
create index ... on sales_order (tenant_id, customer_id, order_date desc);
create index ... on sales_order (tenant_id, fulfillment_warehouse_id, shipment_status, updated_at desc);
```

### 4.2 `sales_order_line`

| 字段 | 类型 | 约束/说明 |
| --- | --- | --- |
| `id`、`tenant_id`、`sales_order_id` | UUID/text/UUID | `unique(tenant_id, sales_order_id, line_no)`；复合外键指向订单 |
| `line_no` | `integer` | `> 0`，订单内稳定不复用 |
| `revision` | `bigint` | 非空且 `>= 1`，影响履约的修改递增 |
| `product_id` | `text` | 非空 |
| `product_code_snapshot`、`product_name_snapshot` | `varchar(80/200)` | 非空 |
| `ordered_qty` | `numeric(18,6)` | `> 0` |
| `uom` | `varchar(20)` | 非空 |
| `unit_price`、`tax_rate`、`line_amount` | `numeric(20,6)` | 均 `>= 0` |
| `shipped_qty`、`active_requested_qty`、`reserved_qty` | `numeric(18,6)` | 非空默认 0，均非负 |
| `remaining_qty` | `numeric(18,6)` | 非空，等于 `ordered_qty - shipped_qty` |
| `allow_partial_shipment` | `boolean` | 非空 |
| `line_status` | `varchar(24)` | `OPEN/RESERVED/PARTIALLY_SHIPPED/SHIPPED/CANCELED` |
| `promised_date` | `date` | 非空 |

行级检查至少包括：`shipped_qty <= ordered_qty`、`remaining_qty = ordered_qty - shipped_qty`、`reserved_qty <= remaining_qty`、`active_requested_qty <= remaining_qty`。累计字段只能由销售应用服务消费唯一库存事实后更新，禁止普通编辑接口写入。

订单编辑传入行集合时按 `line_no` 进行完整集合合并：匹配行保留原 UUID 并提升 `revision`，新行使用从未使用过的行号，缺失行转 `CANCELED` 并保留历史。存在活动发货申请、预留、生产需求或出库事实时禁止替换相关行，不能通过删除重建绕过来源唯一性。

### 4.3 `sales_review_action`

不可变审批流水：`id, tenant_id, sales_order_id, order_version, action, from_status, to_status, actor_id, actor_employee_id, comment, trace_id, acted_at`。`action` 为 `SUBMIT/APPROVE/REJECT/RETURN/CANCEL`；`REJECT/RETURN` 的 `comment` 非空。审批人与订单 `created_by` 的职责分离由服务端权限上下文校验，审计快照同时记录判断依据。

索引：`(tenant_id, sales_order_id, acted_at)`。本表仅允许插入和查询。

### 4.4 `sales_shipment_request`

发货申请聚合根，四个状态轴不得合并为单一展示状态。

| 字段 | 类型 | 约束/说明 |
| --- | --- | --- |
| `request_no` | `varchar(50)` | 租户内唯一 |
| `sales_order_id` | `uuid` | 销售域复合外键 |
| `warehouse_id` | `text` | 创建时仓库快照 |
| `order_revision` | `bigint` | 发起时订单版本 |
| `allow_partial_shipment` | `boolean` | 订单级策略快照 |
| `recipient_snapshot` | `jsonb` | 固定加密结构，电话只含 `phoneCiphertext/phoneKeyId/phoneMasked`；Outbox/Inbox 不得落明文 |
| `workflow_status` | `varchar(32)` | `DRAFT/REQUESTED/PROCESSING/ACTIVE/PROCESSING_UNKNOWN/MANUAL_INTERVENTION/COMPLETED` |
| `availability_status` | `varchar(32)` | `UNCHECKED/CHECKING/PARTIALLY_RESERVED/RESERVED/SHORTAGE/RECHECKING` |
| `replenishment_status` | `varchar(32)` | `NOT_REQUIRED/REQUIRED/REQUESTED/IN_PROGRESS/AVAILABLE/CLOSED/FAILED` |
| `posting_status` | `varchar(24)` | `NOT_STARTED/PARTIALLY_POSTED/POSTED` |
| `inventory_fact_version` | `bigint` | 可空，最近一次校验事实版本 |
| `outbound_id` | `uuid` | 可空，库存域不透明来源 ID，无外键 |
| `production_correlation_id` | `uuid` | 可空 |
| `accepted_at`、`completed_at` | `timestamptz` | 按状态必填 |
| `failure_code`、`failure_message` | `varchar(80/500)` | 失败或人工处理证据 |

索引：`(tenant_id, sales_order_id, workflow_status, updated_at desc)`、`(tenant_id, warehouse_id, workflow_status, updated_at desc)`、`(tenant_id, correlation_id)`。

### 4.5 `sales_shipment_request_line`

字段：`id, tenant_id, shipment_request_id, order_line_id, source_line_revision, product_id, requested_qty, reserved_qty, posted_qty, shortage_qty, uom, allow_partial_shipment, promised_date, production_demand_id, created_at, updated_at`。

约束：

- `unique(tenant_id, shipment_request_id, order_line_id)`。
- `requested_qty > 0`，其余数量非负。
- `posted_qty <= reserved_qty <= requested_qty`，`shortage_qty = requested_qty - reserved_qty`。
- `uom`、产品和来源版本必须与订单行快照一致。
- 在 `sales_shipment_request.workflow_status <> 'COMPLETED'` 时，同一 `order_line_id + source_line_revision` 只能存在一个活动履约链路；实现时在请求行保存冗余 `workflow_terminal boolean`，由同一事务维护，并建立部分唯一索引，避免 PostgreSQL 跨表条件索引。

## 5. 库存域表

### 5.1 `inv_availability_projection`

WMS 权威库存事实的只读投影，主键为 `(tenant_id, warehouse_id, product_id)`。

字段：`qualified_on_hand_qty, allocated_reserved_qty, frozen_qty, safety_stock_qty, in_transit_qty, fulfillable_qty numeric(18,6)`，以及 `uom, formula_version, fact_version, source_system, source_event_id, as_of, updated_at`。

约束：

- 所有数量非负。
- `fulfillable_qty = greatest(qualified_on_hand_qty - allocated_reserved_qty - frozen_qty - safety_stock_qty, 0)`。
- `fact_version >= 1`；只接受同一仓库和产品更高版本，重复事件由 Inbox 去重，陈旧版本记录处理结果但不覆盖投影。
- `unique(tenant_id, source_system, source_event_id)`。
- 在途量仅展示，不进入公式。

索引：`(tenant_id, warehouse_id, as_of)`、`(tenant_id, product_id, as_of)`。该表不等于平台自建库存总账。

### 5.2 `inv_shipment_task`

库存域对销售发货申请的本地聚合投影。字段包括 `id, tenant_id, shipment_request_id, request_no, sales_order_id, sales_order_no, warehouse_id, order_revision, allow_partial_shipment, recipient_snapshot, workflow_status, availability_status, replenishment_status, posting_status, inventory_fact_version, outbound_id, correlation_id, source_aggregate_version, version, created_by, created_at, updated_by, updated_at`。

约束：`unique(tenant_id, shipment_request_id)`；来源聚合版本只能单调前进；状态轴与 OpenAPI 枚举一致。销售域 ID 只作来源引用，不建立外键。

### 5.3 `inv_shipment_task_line`

字段：`id, tenant_id, shipment_task_id, shipment_request_line_id, order_line_id, source_line_revision, product_id, requested_qty, reserved_qty, posted_qty, shortage_qty, uom, allow_partial_shipment, promised_date, production_demand_id, created_at, updated_at`。

约束：`unique(tenant_id, shipment_task_id, shipment_request_line_id)`、`unique(tenant_id, shipment_request_line_id, source_line_revision)`，数量守恒与销售申请行一致。库存服务以本表为编排输入，但必须在 WMS 原子操作前重读权威事实。

### 5.4 `inv_reservation`

每个申请行一条可累积消费/释放的预留记录。一次 WMS 原子操作可以创建多条记录，`inventory.reservation.created.v1` 使用 `reservations[]` 携带每行自己的 `reservationId`，不得用一个预留 ID 代表多条数据库记录。

字段：`reservation_no, shipment_task_id, shipment_request_id, sales_order_id, order_line_id, product_id, warehouse_id, requested_qty, reserved_qty, consumed_qty, released_qty, status, fact_version, formula_version, external_reservation_id, expires_at, release_reason, version, correlation_id, created_by, created_at, updated_by, updated_at`。

约束：

- `unique(tenant_id, reservation_no)`。
- `unique(tenant_id, shipment_request_id, order_line_id, fact_version)`，同一事实版本重试不重复预留。
- `unique(tenant_id, external_reservation_id)`，使用 `where external_reservation_id is not null` 部分唯一索引。
- `0 < reserved_qty <= requested_qty`；`consumed_qty + released_qty <= reserved_qty`。
- `status` 为 `PENDING/PARTIAL/ACTIVE/CONSUMED/RELEASED/EXPIRED/FAILED`。
- `CONSUMED/RELEASED/EXPIRED/FAILED` 终态记录不可删除；部分消费或释放写不可变明细。

### 5.5 `inv_reservation_movement`

为避免只保存累计数，新增不可变数量明细：`id, tenant_id, reservation_id, movement_type, qty, external_transaction_id, compensation_id, reason, actor_id, trace_id, occurred_at`。`movement_type` 为 `RESERVE/CONSUME/RELEASE/EXPIRE`，`qty > 0`；外部流水与动作类型租户内唯一。聚合累计值必须等于明细汇总。

### 5.6 `inv_sales_outbound` 与 `inv_sales_outbound_line`

出库聚合根字段：`outbound_no, shipment_task_id, shipment_request_id, sales_order_id, warehouse_id, status, external_outbound_id, posting_key, posted_at, failure_code, failure_message` 加公共聚合字段。

- `status` 为 `CREATED/RESERVED/POSTING/PARTIALLY_POSTED/POSTED/PROCESSING_UNKNOWN/MANUAL_INTERVENTION/FAILED`。
- `unique(tenant_id, outbound_no)`、`unique(tenant_id, shipment_request_id)`、`unique(tenant_id, posting_key)`。
- `external_outbound_id` 非空时租户内唯一。

出库行字段：`id, tenant_id, outbound_id, order_line_id, product_id, requested_qty, reserved_qty, posted_qty, uom, batch_allocations, created_at, updated_at`。约束 `unique(tenant_id, outbound_id, order_line_id)`、`0 <= posted_qty <= reserved_qty <= requested_qty`。`batch_allocations` 只保存 WMS 证据。

### 5.7 `inv_transaction`

不可变库存流水投影。字段：`transaction_no, external_transaction_id, transaction_type, warehouse_id, product_id, qty, uom, source_type, source_id, source_line_id, reversal_of_transaction_id, fact_version, occurred_at, payload_snapshot, correlation_id, trace_id, created_at`。

- `transaction_type` 首期为 `SALES_OUTBOUND/FG_COMPLETION_INBOUND/RESERVATION_RELEASE`；未来冲正使用独立反向类型，不修改原行。
- `unique(tenant_id, transaction_no)`、`unique(tenant_id, external_transaction_id)`。
- `qty > 0`，方向由类型决定。
- `reversal_of_transaction_id` 只引用本域且同租户原流水；原流水仍不可变。

索引：`(tenant_id, warehouse_id, occurred_at desc)`、`(tenant_id, product_id, occurred_at desc)`、`(tenant_id, source_type, source_id, occurred_at)`。

## 6. 共享可靠性与审计表

### 6.1 `shared_idempotency_record`

字段：`id, tenant_id, domain, command_type, idempotency_key, request_hash, status, response_status, response_body, aggregate_type, aggregate_id, trace_id, expires_at, created_at, updated_at`。

约束 `unique(tenant_id, domain, command_type, idempotency_key)`；同键不同请求哈希返回 409。业务写入的幂等记录保留期不得短于客户最大重试和对账窗口；实际出库、预留和补偿命令建议长期保留哈希与结果定位，不只保留 24 小时。

### 6.2 `shared_status_history`

不可变字段：`tenant_id, domain, aggregate_type, aggregate_id, aggregate_version, state_axis, from_status, to_status, reason_code, reason, actor_id, trace_id, metadata, occurred_at`。四轴发货状态分别记录 `state_axis`，不得只记录页面派生标签。

### 6.3 `shared_audit_snapshot`

不可变字段：`tenant_id, domain, action, aggregate_type, aggregate_id, aggregate_version, actor_account_id, actor_employee_id, permission_version, data_scope_snapshot, before_snapshot, after_snapshot, reason, trace_id, ip_address, user_agent, occurred_at`。电话、地址和外部凭据按字段脱敏或密文保存，审计快照不得形成明文泄漏旁路。

### 6.4 `integration_event_outbox`

字段符合基线事件信封，并补充 `status, retry_count, max_retry_count default 8, next_retry_at, locked_by, locked_at, last_error_code, last_error_message, created_at, published_at`。

约束：`unique(tenant_id, event_id)`；状态为 `PENDING/PUBLISHING/PUBLISHED/RETRY_WAIT/DEAD_LETTER/MANUAL_INTERVENTION/ABANDONED`。Worker 索引使用 `(status, next_retry_at, created_at)`，领取使用 `for update skip locked`。同一聚合按 `aggregate_version` 发布，不能用新事件 ID替代失败事件。

### 6.5 `integration_event_inbox`

字段：完整事件信封、`consumer_name, status, retry_count, next_retry_at, last_error_code, last_error_message, payload, received_at, processed_at`。

约束：`unique(tenant_id, consumer_name, event_id)`；状态为 `RECEIVED/PROCESSING/PROCESSED/RETRY_WAIT/DEAD_LETTER/DUPLICATE/MANUAL_INTERVENTION`。索引 `(tenant_id, consumer_name, aggregate_id, aggregate_version)` 支持乱序检测，`(status, next_retry_at, received_at)` 支持 Worker。

### 6.6 `integration_compensation`

聚合字段加：`compensation_no, business_type, source_domain, source_aggregate_type, source_aggregate_id, source_version, reason_code, reason, affected_qty, uom, evidence, before_snapshot, proposed_action, after_snapshot, status, requested_by, business_confirmed_by, approved_by, executed_by, trace_id, requested_at, approved_at, executed_at, closed_at`。

状态为 `DRAFT/PENDING_BUSINESS_CONFIRMATION/PENDING_APPROVAL/APPROVED/EXECUTING/EXECUTED/CLOSED/REJECTED/FAILED`。发起人、业务确认人、审批人和执行人的职责分离在服务层校验并进入审计；本表不能直接触发 SQL 改库，执行必须调用有幂等和审计的领域命令。

## 7. 租户隔离与权限数据

1. 所有上述表执行 `enable row level security` 和 `force row level security`。
2. 策略使用 `tenant_id = current_setting('app.tenant_id', true)`；事务开始后先设置租户，未设置时查询返回空、写入失败。
3. Bearer Token 的 `tenantIds` 是租户授权权威来源，`X-Tenant-Id` 只从中选择本次租户；服务端必须在开启数据库事务和设置 `app.tenant_id` 前完成令牌校验和成员关系校验。
4. 表所有者不作为运行账号；运行账号不得拥有 `BYPASSRLS`。迁移账号和受控运维账号分离。
5. 应用层查询仍显式包含 `tenant_id`，RLS 是纵深防御，不代替仓储过滤。
6. 数据范围字段保留 `owner_employee_id`、`owner_org_id`、`warehouse_id`、`factory_resource_id`，供权限中心下发范围后在 SQL 层过滤；禁止查全租户后由前端过滤。
7. 跨域事件的信封 `tenant_id` 必须与载荷来源一致；消费时以可信集成上下文设置租户，不接受普通前端任意指定内部事件租户。内部事件的租户头、时间戳、密钥 ID 和原始请求体必须共同参与签名。

## 8. 事务边界与并发

### 8.1 销售创建发货申请

同一事务：锁定订单及涉及行；校验审批、状态、剩余量和活动申请；写申请及行；增加 `active_requested_qty`；写状态历史、审计、幂等结果和 `sales.shipment-request.requested.v1` Outbox；提交后由 Worker 发布。

### 8.2 库存校验和预留

平台不得仅凭投影表自行承诺 WMS 库存。库存服务以稳定 `postingKey` 调用 WMS 原子校验/预留：

- 明确成功：同一数据库事务写/更新任务、预留、预留明细、出库单、历史、审计和 Outbox。
- 明确不足：写事实版本、缺口、历史和 `inventory.shortage.detected.v1` Outbox。
- 超时或未知：任务进入 `PROCESSING_UNKNOWN`，记录原键和重查任务；不得创建第二次预留。

数据库唯一约束是最后防线，不能代替 WMS 原子并发控制。

### 8.3 出库过账与销售回写

WMS 外部流水第一次到达时，库存事务写 `inv_transaction`、累计出库行和预留消费、推进出库/任务状态并写部分或全量出库 Outbox。销售消费事件时先 Inbox 去重，再锁定订单行并原子更新 `shipped_qty/remaining_qty`、订单状态、历史和审计。重复或陈旧聚合版本不得再次累计。

### 8.4 完工入库与重新校验

生产完工 `POSTED` 事件先进入库存 Inbox。若事件只含 WMS 外部流水而没有新 `factVersion`，库存记录流水但等待 WMS 更高版本可用量事实；只有权威事实到达后才能重新校验关联任务。不得把生产完工数量直接加到销售可用量投影。

## 9. 与现有数据库的兼容

### 9.1 `prod_inventory_availability`

现表只有 `available_qty`，缺少 `qualified_on_hand_qty`、`allocated_reserved_qty`、`frozen_qty`、`safety_stock_qty`、`in_transit_qty` 和 `formula_version`。这些组成项无法从汇总值可靠反推，因此：

1. 不使用 SQL 将旧 `available_qty` 冒充 `qualified_on_hand_qty` 作为客户正式数据。
2. 新建 `inv_availability_projection` 后，由 WMS 全量快照初始化组成项和 `factVersion`。
3. 初始化完成前，正式销售履约保持阻断；开发环境可显式使用 `LEGACY_DEMO` 来源，但不能进入 UAT 证据。
4. 完成总量、组成项、单位、时效和版本抽查后，生产兼容接入改读新库存服务；旧表转只读观察。
5. 至少经过一个对账周期且无旧调用后，再通过单独收缩迁移删除旧表，不能与建表迁移同批执行。

### 9.2 `prod_sales_order_intake`

该表继续作为生产兼容接入记录。库存生产申请在来源快照中补充 `shipmentRequestLineId`、`orderLineId` 和来源版本；优先采用后续迁移增加结构化列和唯一索引，不把关联只塞入 JSON。生产需求已经创建后不得重建，恢复调用返回既有 `demand_id`。

### 9.3 现有生产治理表

现有 `prod_event_*`、`prod_idempotency_record`、`prod_status_history` 和 `prod_audit_snapshot` 继续服务生产域。首期销售/库存使用新的共享表；不在本期强制搬迁生产历史。后续统一治理需要单独迁移、双读验证和保留原 ID，不能简单重命名造成生产服务停机。

## 11. 回滚与恢复

### 11.1 切换前

迁移均为新增表时，可回滚应用版本并保留空表；不删除生产现有结构。失败迁移必须使用配对回退脚本移除本次未使用对象，不使用手工改库。

### 11.2 已写业务事实后

一旦生成订单、预留、出库、库存流水或事件，禁止通过 `down` 迁移删除数据。应用问题优先回退读写开关并保留新表，随后前向修复。WMS 已成功但平台未知时先按原幂等键重查和对账，不回滚为“未发生”。

### 11.3 灾难恢复

- 上线前验证 PITR、备份恢复、RPO/RTO 和加密密钥恢复。
- 恢复后按 `external_transaction_id`、`event_id` 和 `fact_version` 对账，重放使用原 ID。
- Outbox/Inbox、审计、状态历史和补偿记录与业务表采用一致备份时间点。
- 恢复环境必须重新设置 RLS、运行账号和密钥，不复制生产明文凭据。

## 12. 数据初始化与验收查询

上线前必须生成版本化初始化报告，至少包含：客户/产品/单位/仓库/工厂映射，审批策略版本，WMS 全量事实时间点，缺失/重复/陈旧事实，以及试点产品齐套结果。

核心一致性检查：

1. 订单金额等于有效行金额汇总；行剩余量等于订购量减累计已发量。
2. 活动发货申请量不超过对应行剩余可申请量。
3. 申请行满足 `requested = reserved + shortage`，出库累计不超过预留。
4. 预留累计等于预留明细的预留减消费减释放。
5. 每个 WMS 外部预留和流水唯一；重复事件不改变累计量。
6. 可履约量按组成项复算一致，版本单调，单位映射完整。
7. `SHIPPED` 订单所有行 `shipped_qty = ordered_qty`。
8. 业务聚合、状态历史、审计和 Outbox 的 Trace/Correlation 可完整串联。
9. 所有业务表启用并强制 RLS；跨租户查询、写入和关联测试失败。
10. 死信、处理中未知和待补偿记录均有责任人，不允许带未解释差异上线。
