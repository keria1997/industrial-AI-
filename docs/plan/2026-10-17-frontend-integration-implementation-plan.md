## 1. 本轮结论

**可以开始前端整改，但当前不能认定“接口契约完整、前后端一致、业务已经闭环”。**

已确认的前端问题包括：销售售后读取字段不匹配、售后办理入口缺失、物料仓库字段未提交、工作台刷新与翻页混用、部分平台命令仍被旧拦截阻断、忘记密码使用了不匹配的提交协议，以及业务表单仍存在固定事实兜底。

另外存在必须由后端或产品先解决的依赖：工作台 1.1 响应结构及数据权限、财务确认和核销重复扣减风险、冲销余额恢复逻辑、RMA 驳回状态机、签收补签及争议处理、关闭检查标识来源、部分新增命令的操作权限。前端增加按钮不能补齐这些领域规则。

本轮运行 `npm run verify:api-contracts` 通过，结果为 **306 条 Spring 路由、306 个生成 OpenAPI operation**，其中 `public=295`、`internal=4`、`retired=7`。这项检查只证明路由覆盖一致，不能证明字段、权限、响应或数据库事实一致。生成 OpenAPI 没有 DTO schemas，也没有 operation requestBody，仍需模块契约补齐。

**本轮没有执行浏览器业务写入、数据库比对或真实邮件发送。下文的运行风险属于源码静态确认，实际影响范围仍须通过专用测试环境验证。**

```text
    sales/components/        RMA/签收/完成检查及办理表单
    finance/components/      台账、核销事实、冲销办理
    inventory/pages/         主数据与库存页面
    production/              现有 BOM/报工/排程组件与模型
    procurement/             现有申请、订单、收货能力
    ai-hub/                  AI 业务交互与数据导入
  platform/                  平台及员工账号页面
  shared/                    十进制、验证、格式与已批准缓存策略

```

可按实际复杂度在现有 features 下增加表单，不整份重写 App、不新建另一套前端、不启用未引用组件替代实际入口。文件命名、路由参数、菜单顺序和已有布局保持既有约定。

### 6.2 查询与响应

- 继续使用 `api/client.ts`；单据、分页集合、业务命令结果、204 分别处理。禁止对所有响应统一 `.data` 解包。
- Workbench 1.1 的 `.data` 是该模块正式 schema 的组成部分，必须由专用 projection 检查。
- 活跃查询的 key 至少包含 tenantId、账号/签名身份、权限/范围版本、筛选及分页；退出、换租户、权限刷新时清除旧数据及选择。
- 使用 AbortController 或请求世代号屏蔽迟到响应。同一 scope 内也防止搜索/分页旧请求覆盖新结果。
- 不同权限的分区分别查询并呈现局部错误；不能让无权读取技能阻断员工列表。
- 列表 total 来自正式分页，不使用当前页长度伪装总数；完整集合读取须处理后续页和服务端上限。
- 未知状态显示原状态或“状态待核实”，不默认映射为已完成/正常。

### 6.3 写命令与重试

每次提交冻结 `tenant + actor + aggregateId + action + expectedVersion + payload + idempotencyKey`，提交中防重复。

| 结果 | 前端行为 |
| --- | --- |
| 成功且取得权威结果 | 更新对应实体，刷新受影响列表/统计/版本；提示具体动作完成 |
| 成功但后续刷新失败 | 提示“操作已提交，刷新失败”，允许重新查询；不能把命令当失败再次新建 |
| 超时/断网/未知结果 | 保留同一 payload、版本和 key，先查询或原样重试；不能随机换键 |
| 字段/业务失败 | 保留输入并定位字段；用户修改后创建新提交上下文 |
| 版本或状态冲突 | 拉最新版本、展示差异并让用户重新确认；不能静默加一或自动套最新版本覆盖 |
| 401/403/租户改变 | 停止旧上下文提交，清敏感选择；业务草稿不能进入另一个租户 |

If-Match、幂等、trace 等按各操作正式契约传递。新建没有历史聚合版本时不伪造 If-Match；同样不能遗漏协议已要求的版本。保留模块业务码、fieldErrors、suggestion 和 traceId。

### 6.4 金额、数量与来源

- 输入草稿保留字符串，可清空；提交时校验并规范化，不在每次输入时把空串强制设为 0。
- 正式金额和数量保持十进制字符串；优先扩展现有共享工具处理精度。现有数量工具只接收非负数，红字/冲销金额需独立有符号规则，不能直接复用导致拒绝合法红字。
- 不跨币种求和；无正式换算汇率不生成“全盘人民币”。税口径、精度、舍入及业务日期按冻结协议。
- 数量仅在同一计量单位或明确换算后汇总。稳定业务 ID、展示编号、资源 ID、编码分别建模。
- 缺默认仓库、收货资料、资源映射时要求选择/补录，不填虚构手机号、地址、供应商或工作中心。
- 正式业务数据只来自后端 API。允许本地表单草稿和提交恢复上下文，不允许持久化模拟余额、订单状态、流水、AI 结论或趋势。
- 保留合法登录会话、租户偏好及必要恢复记录；仅清理已识别的原型业务键，禁止 `localStorage.clear()` 或删除数据库数据。

## 7. 模块实施设计

### 7.1 RMA 办理

先修读取 DTO，再增加命令 client 与表单。创建从真实订单/已过账出库行选来源，展示已退/占用及可退数量；数量上限由后端复核。证据按 `{url,name?,type?}`，没有上传契约时不生成虚假附件地址。

| 动作 | 表单与协议重点 | 开放依赖 |
| --- | --- | --- |
| 创建 | orderId/outboundId/outboundLineId/requestedQty/reason/evidence；不填写 approvedQty | B-05/B-07 的来源、权限与响应明确 |
| APPROVE | decision/comment，批准时 approvedQty/expectedCreditAmount/currency；驳回条件字段单列 | B-05 修复 REJECT 枚举及状态机 |
| TRANSIT_UPDATE | carrier/trackingNo/shippedAt | B-05 逐动作字段及物流事实 |
| RECEIVE | receivedQty/warehouseId，按规则补批次/序列号 | B-07 授权仓库与数量上限 |
| START_INSPECTION | 合法当前状态和目标状态 | B-05 |
| INSPECT | qualifiedQty/reworkQty/scrapQty/result，报废理由按条件必填 | 数量守恒与处置规则 |
| RESTOCK | restockedQty/warehouseId/location/inventoryIdempotencyKey 等冻结字段 | B-07 库存事实与追溯 |
| CREDIT_NOTE | currency/reason/lines 及已澄清的金额/税口径 | B-03/B-05，已付款退货规则 |
| CLOSE | closureCheckId/comment，不自造检查 ID | B-05，库存/贷项/争议条件 |

每次迁移使用服务端版本。展示 transitionHistory、操作者及来源事实，不用本地生成历史替代。

### 7.2 客户签收与销售完成

1. 明确“发货完成 ≠ 客户正常签收 ≠ 销售完成关闭”。分别展示 overallStatus、receiptStatus 和完成事实。
2. 签收从订单与出库事实读取待登记行；用户录入 signed/rejected/damaged 等正式字段，不提交伪造 shippedQty。
3. 按契约校验数量，展示未处理余量；同一来源行重复、漏行、超量及跨单位分别处理。
4. 创建正常签收先接入；B-06 未完成前部分签收、拒收及争议续办标明阻断，最终验收仍必须覆盖这些分支。
5. “完成关闭”先调用 complete-check 并携带预期版本，展示 missingConditions；可完成后再显式确认调用 complete。
6. complete-check 是预检，complete 仍需后端原子复核全部来源 AR，以及按 REQUIRED 标记要求的发票/凭证。预检与提交间发生新退货、余额或版本变化必须冲突，不自动改为成功。
7. 查询订单确认状态及关闭引用。receiptId/arAllocationCheckId 是否由前端传入按 B-05 的冻结结论实施。

### 7.3 财务台账、核销与冲销

- 新增明确的合并台账、核销事实列表和冲销表单；现有收付款登记表单继续执行登记语义。
- 遵循 PRD“确认收付款原子生成核销事实并更新余额”。前端确认后读取关联 Allocation，不再次为同额自动 POST allocations。
- 独立核销仅在已冻结协议确实存在未核销收付款余额时开放，展示累计已核销/可核销余额及同往来方、方向、币种候选单据。
- 冲销填写理由，引用真实审批授权/凭证；展示影响及版本。取得 reverseFinanceId 后刷新原单、反向单、核销和 AR/AP。
- 已冲销状态不得继续确认/分配；失败保持草稿，不在客户端恢复余额或删除核销事实。
- B-03/B-04 未通过时可开发类型、展示和错误处理，核销/冲销写入验收保持阻断。

### 7.4 库存、生产、采购

- 物料仓库与产品已有选项机制复用，统一标签“库存仓库”，提交真实仓库 ID；产品新增允许不关联，修改可关联/替换。当前后端未提供取消既有关联的确定语义，前端明确阻断取消，待 B-09 后开放。
- 仓库选择同时检查加载失败、空选项、停用、无权、保存前变更及 409；仓库关联不是库存转移。
- 生产在现有运行入口修复资源选择、任务结果和版本刷新；BOM 输入使用实际产品/物料/仓库/工作中心，不依赖固定 ID。
- 生产完工、检验、入库与结案依次读取真实事实，不能用良品报工等同库存已经增加。
- 采购沿 MRP 来源行、PR、PO、收货/IQC、库存及 AP 建立穿透。PR/PO/收货数量及金额使用正式行与版本。
- 手工入库、盘点、调拨、退料、委外等按 B-10 分项接入；没有能力的功能保留未完成，不用库存内部回调或 localStorage 模拟。

### 7.5 平台与认证

- 保留 `persistPlatformChange` 已有的单命令保护，在现有适配机制中补充明确的 tenant 编辑、adapter 同步命令；一次保存只执行对应业务动作，不能“同步”时修改无关配置。
- 账号页传递完整 ApiContext；保留 Auth 域 status PUT 的 204 和 reset-password 的 temporaryPassword 响应，处理 forced-first-login。
- 角色授权继续使用有效权限目录及服务端版本，发布后重新刷新授权；岗位名称不授予角色权限。
- 找回页支持“申请验证码邮件→通用受理提示→邮箱验证码与新密码→重新登录”，邮件链接进入独立重置页并补邮箱，按当前 email/code/newPassword 协议提交；不展示开发验证码、不持久化码和口令。受理与真实邮件送达分开验收。
- 手机号初始为空；短信发送中的号码变化、倒计时与服务端限流明确处理；成功会话登录方式正确。
- 退出调用服务端 logout；本机清理、服务端撤销成功/未知分别处理，不缓存敏感口令。
- 人员管理保持考勤、排班及相关指标隐藏，员工档案无新增/导入/导出；平台员工/账号维护按其独立权限和 PRD 保留。

### 7.6 其余模块

- 产业链修类型/枚举、分区查询与来源跳转，策略/附件等待独立契约。
- AI 所有推理、prompt、RAG、Agent 留在 AI 服务；前端只提交业务输入、展示后端结果和处理审批。
- 当前 `/api/v1/ai/chat` 是 JSON 通信；`docs/api-contract.md` 的 `/chat/*` SSE 是早期目标，不能直接接入或声称已实现流式验收。
- 导入修格式支持、授权实体、异步隔离、仓库字段、幂等与部分成功；文件解析/列匹配作为输入处理，不在前端实现 LLM。
- 消息按正式来源类型定位目标记录；业务状态从业务 API 查询，不把已读/归档当作业务待办关闭。
- 分析和问题反馈等未完成项绑定 PRD 条目与契约依赖，不能用“空态已显示”关闭功能需求。

### 9.2 页面、API、数据库三方一致

真正端到端路径为：

```text
Playwright 操作页面
  → 捕获业务后端请求、响应和 trace
  → 通过只读数据库连接按 tenantId + 业务ID 查询事实
  → 对比单据、版本、数量/金额、关联事实及事件
  → 页面刷新或新会话重新查询
  → 再次比对 API 与页面结果
```

浏览器不直连数据库。数据库查询由测试工具或后端执行，以当前 JDBC Store、集合/表映射为准，不臆造 `sales_orders` 等表名，不通过数据库直接造终态来让用例通过。

前置准备：

1. 确认 `127.0.0.1:8081` 的实际运行提交、profile、数据源及 PostgreSQL `industrial_ai`；不能只根据源码推定运行环境。
2. 使用专用测试租户，至少两个租户、两个独立办理人，以及只读/销售/仓库/计划/采购/财务/管理员低权限账号。
3. 记录真实产品、物料、仓库/资源、客户/供应商、BOM及来源行 ID，避免依赖固定 FAC/WH 编码。
4. 建立带唯一测试标记的最小业务数据；真实写入前确认测试隔离。证据中脱敏 token、口令、个人联系方式。
5. 数据清理由后端认可的业务撤销/冲销流程或测试环境策略执行；不删除真实历史记录。

每条证据至少记录：用例 ID、提交/环境、tenant、操作者、源单/行/聚合 ID、请求动作与预期版本、traceId、幂等键的脱敏引用、响应、数据库前后事实、页面截图及结论。只记录 HTTP 200 不算通过。

### 9.3 必须跑通的业务链

| 链路 | 核对的权威事实 |
| --- | --- |
| 现货销售→确认→发货申请→预留→出库过账→AR→客户签收→收款确认/核销事实→完成关闭 | 发货/库存数量、AR余额/核销、签收行、关闭事实各自成立且关联同源 |
| 缺货销售→生产需求→MRP→PR→PO→收货/IQC→物料入库/AP→生产/检验→成品入库→补发→销售后续 | 来源行、任务/版本、库存流水、AP、工单与最终发货均可追溯 |
| 部分发货→续发→部分签收→补签/争议处理→关闭 | 已发/签收累计不超量、余量清晰、不丢行、不提前完成 |
| RMA→通过/驳回→物流→收货→检验→回入库/返工/报废→贷项或退款/抵扣→关闭 | 数量守恒、库存处置、财务关联及独立关闭检查；驳回不占可退额度 |
| 财务登记→独立确认→核销事实→冲销 | 原单、反向单、AR/AP余额、核销与事件一致，无重复扣减 |
| 平台授权/租户切换→业务读写→消息/工作台穿透 | 授权与范围版本生效，展示角色不扩权，消息只读/归档不改变业务状态 |
| 注册→初始化/授权→登录→邮件找回/首次改密→退出 | 登录身份与业务角色分离，token 流转完整，敏感凭证不持久化 |

B-05/B-06 等未解除时，相关异常链必须记录“阻断”，不能以正常链成功替代整个模块通过。

## 10. 交付与验收门槛

前端实施产生代码后，交付内容应包含：

1. 已冻结契约及变更清单，PRD/技术设计需要调整的口径有明确确认记录。
2. FE 任务逐项状态、对应提交、自动检查和真实联调用例证据。
3. 每个模块的 PRD 条目→页面/动作→API→数据库事实→验收用例对应关系；缺失或多余功能均有处理结论。
4. 后端阻断逐条解除证据；待确认项不得默认为已接受或已实现。
5. 文档与代码 diff 审查，相关检查通过后仅提交当前任务文件并正常推送，保留其他未提交工作。

最终通过条件：

- 所有 PRD 必验能力完成；待办/消息穿透真实记录，页面没有本地模拟业务事实或假成功。
- RMA、签收异常续办、财务与销售完成关闭均有数据库证据；任何关键阻断未解除，整体联调不得标记完成。
- 不同身份和租户的权限用例通过，且前端隐藏不替代服务端授权。
- 默认态、错误态及重试不会伪造零值、趋势、AI建议或业务终态。
- 考勤/排班及其人员监控信息继续按用户要求隐藏，员工档案保持只读展示与搜索。

本计划已进入执行。已实施的前端修复及测试结果见同目录执行报告；数据库一致性验收和全部 PRD 能力仍未完成，不得把已交付的前端修复等同于整体联调通过。
