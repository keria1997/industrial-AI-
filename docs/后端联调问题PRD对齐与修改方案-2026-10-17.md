# 后端联调问题 PRD 对齐与修改方案

日期：2026-10-17。范围来源：《前后端真实联调报告-2026-10-17》第 41-53 行列出的后端闭环缺口，以及 PRD 第 7.3.2、7.3.9.2.6、7.3.9.2.7、第 17 章 P0 闭环契约。本文只冻结修改方案和验收边界，不把当前实现顺势解释为需求。

## 1. 对齐原则

1. PRD 是唯一业务口径。当前接口路径、字段名和状态流若与 PRD 不一致，必须先冻结契约，不允许为了减少前端改动而缩小 PRD。
2. PRD 第 17 章已确认销售 RMA、客户签收、平台内 AR/核销和销售完成关闭属于 P0，全部实现、不分期；不能用 77 项读取一致性通过替代这些命令链路验收。
3. 历史单据缺事实时只能进入受审核的数据治理，不能由后端自动补单、自动生成红字 AR 或改写状态。
4. 命令接口必须保留租户、Bearer Token、权限、幂等键、版本、来源 ID、Correlation ID、审计和事件；错误必须可回滚、可重试、可追踪。

## 2. 必须先决策的 PRD 冲突

以下冲突影响主流程，不能默认处理。

| 编号 | 冲突 | PRD 口径 | 当前实现 | 影响与处理要求 |
| --- | --- | --- | --- | --- |
| C-01 | RMA 办理契约不一致 | `POST /rmas/{id}/transition`，通过 `transition/toStatus/comment` 推进状态；状态包含 `IN_TRANSIT`、`RECEIVED`、`INSPECTING`、`RESTOCKED` 等 | 当前前端联调清单使用 `/approve`、`/inspect`、`/close` 三个独立接口 | 直接保留三个接口会跳过 PRD 状态机。建议实现 PRD 的统一 transition 为唯一写入口，旧路径最多作为显式登记的兼容适配器，且必须复用同一状态机；产品确认前不得继续扩展旧路径。 |
| C-02 | 红字 AR 字段不一致 | RMA 事实字段为 `creditNoteFinanceId`，红字 AR/折让是财务域事实 | Controller 与前端当前展示 `creditArId` | 必须新增 PRD 的 `creditNoteFinanceId` 作为稳定关联；`creditArId` 只能作为兼容展示别名，不能替代财务引用。 |
| C-03 | 客户签收创建契约不一致 | `POST /sales-orders/{id}/receipts`，按订单创建签收聚合 | 当前创建入口是 `POST /fulfillment/customer-receipts` | 当前路径可作为列表查询，但不能继续作为 PRD 创建命令。需要产品确认旧路径下线时间；迁移完成前，完成关闭不得消费旧命令产生的事实。 |
| C-04 | 签收状态字段不一致 | `receiptStatus` 是正式状态字段 | 新写入使用 `status`，历史数据主要使用 `receiptStatus`，前端做双读 | `receiptStatus` 必须成为唯一持久化正式字段；`status` 只能是只读兼容别名。不能让两个状态同时可写。 |
| C-05 | 历史已关闭 RMA 缺红字 AR | 关闭前必须有回入库、红字 AR/折让、处置和审批完成事实 | `rma-seed-001` 已为 `CLOSED`，但对应租户 finance/receivable 匹配 0 条且缺币种 | 不能自动补一张红字 AR 来解释历史。该记录进入数据治理台账；若其原销售订单要走完成关闭，必须先阻断并人工审核原始退货、库存和财务凭证。 |
| C-06 | SLA 权限码命名风格不一致 | PRD 写作 `SALES_SETTINGS_MANAGE` | 后端现有资源码多数为点分小写 | 需要确认 PRD 中的代码是否按字面登记。未确认前不能把现有其他销售权限码当作等价资源。 |

## 3. RMA 与红字 AR

### PRD 对齐范围

PRD 7.3.9.2.6、`BIZ-004`、`DEC-012`、`SC-FULL-006` 和验收 `AC-PH1-077` 要求：

- RMA 独立于原销售订单，不修改原订单 `shippedQty` 和 `SHIPPED` 状态。
- RMA 必须关联原订单、原出库单、原出库行、原发货确权事实。
- 状态机为 `REQUESTED`、`APPROVED`、`IN_TRANSIT`、`RECEIVED`、`INSPECTING`、`INSPECTION_COMPLETED`、`RESTOCKED`、`CLOSED`，另有 `REJECTED` 终态。
- 数量守恒：`requestedQty <= 原出库行已发数量 - 已RMA数量`；`receivedQty <= approvedQty`；`qualifiedQty + reworkQty + scrapQty = receivedQty`。
- 合格品回入库生成 `SALES_RETURN` 流水；红字 AR/折让按原发货确权行金额和批准退货数量计算。
- 创建时 `approvedQty` 必须为空；审批时制单人与审批人分离。

### 修改方案

1. **先冻结契约**：按 C-01/C-02 输出 OpenAPI。请求和响应必须包含 `rmaId`、`orderId`、`outboundId`、`outboundLineId`、原始发货确权事实版本、`requestedQty`、`approvedQty`、`receivedQty`、`qualifiedQty`、`reworkQty`、`scrapQty`、`status`、`transitionHistory`、`creditNoteFinanceId` 和 `version`。
2. **补状态机服务**：RMA 命令收敛到一个应用服务；Controller 不再做状态判断。服务端按 PRD 校验当前状态、目标状态、角色、租户、行级来源和数量守恒。
3. **审批与预计红字金额**：审批人必须不同于创建人；审批入参包含 `decision`、`comment`、财务确认的预计红字金额和币种。通过后才允许进入 `APPROVED`，同时生成预期回入库任务。
4. **物流、收货、检验**：`IN_TRANSIT` 记录承运商、运单和发货时间；`RECEIVED` 由仓管录入实收实绩；`INSPECTING` 后录入合格、返修、报废数量和证据。实收允许小于批准量，但不得超批准量。
5. **回入库**：`RESTOCKED` 前必须由库存域生成 `SALES_RETURN` 入库流水并更新库存事实。RMA 服务只消费库存确认事实，不直接更新库存聚合。
6. **红字 AR/折让**：由财务域按 `finance.rma.credit-note.create` 创建，金额按原发货确权行和批准退货数量计算，币种继承原 AR；不超原 AR 可冲销余额。RMA 关闭前校验 `creditNoteFinanceId` 指向租户内有效的负向 AR/折让事实。
7. **关闭**：`CLOSED` 只能在回入库、红字 AR/折让、报废/返修处置、审批全部完成后执行；入参必须有 `closureCheckId` 和 `comment`。关闭失败时所有未完成写入回滚，幂等键重放返回原结果。
8. **历史数据治理**：按 C-05 登记缺失事实，不改写历史。相关订单进入完成关闭前被阻断。

### 验收

- 专用单据走完 `REQUESTED -> APPROVED -> IN_TRANSIT -> RECEIVED -> INSPECTING -> INSPECTION_COMPLETED -> RESTOCKED -> CLOSED`。
- 已发货 10、退回 3、合格 3：库存增加 3，红字 AR 为 `-3` 对应的确权金额，原订单和原 AR 不被删除或覆盖。
- 超可退数量、非制单人审批、缺失 `If-Match`、错误状态迁移、数量不守恒、红字 AR 缺失分别得到 409/422/403，并回滚。
- 重启后 RMA、库存流水和红字 AR 仍一致；重复幂等命令不重复入库或开票。

## 4. 客户签收与销售完成关闭

### PRD 对齐范围

PRD 7.3.9.2.7、`DEC-014`、`SC-FULL-005/011` 和验收 `AC-PH1-076/082` 要求：

- 客户签收是独立事实，不得通过改销售订单状态伪造。
- 已全量发货订单才能登记签收聚合，租户/订单内唯一。
- 正式状态是 `receiptStatus`：`PENDING`、`PARTIALLY_SIGNED`、`SIGNED`、`REJECTED`、`DISPUTED`。
- 行级必须保存 `orderLineId`、`outboundLineId`、`shippedQty`、`signedQty`、`rejectedQty`、`damagedQty`。
- 原出库事实变化后必须重新校验；签收不覆盖出库。
- 销售完成要求全部行签收量等于已发量、拒收/破损有 RMA 或折让、`receiptStatus=SIGNED`、AR `SETTLED`、无未关闭 RMA/争议。

### 修改方案

1. **命令路径对齐**：按 C-03 实现创建命令 `POST /api/v1/sales-orders/{id}/receipts`。`GET /api/v1/fulfillment/customer-receipts` 可继续作为查询列表，但不再承担创建事实。
2. **服务端事实优先**：请求只提供行级签收、拒收、破损、备注和证据；`shippedQty`、`outboundLineId` 对应的已发数量、单位和来源版本全部由服务端从出库事实读取。删除对请求体 `totalShippedQty` 的信任。
3. **行级守恒**：每行校验 `signedQty + rejectedQty + damagedQty <= 该行已发数量`，并累计已有签收聚合，避免分批重复登记。若三者和小于已发量，状态为 `PARTIALLY_SIGNED`；存在拒收/破损/争议时进入 `REJECTED/DISPUTED` 并要求后续 RMA、折让或补偿事实。
4. **字段统一**：持久化和命令响应使用 `receiptStatus`；`status` 只在只读投影中兼容。聚合并发使用 `version`/`If-Match`，创建和更新都要幂等键。
5. **事件**：签收状态变化发布 `sales.receipt.partially_signed/signed/rejected/disputed`，事件携带来源订单、来源出库版本、Correlation ID 和 Trace ID。
6. **完成关闭**：实现 PRD 的 `POST /api/v1/sales-orders/{id}/complete-check` 和 `POST /api/v1/sales-orders/{id}/complete`。完成前逐项校验全部行已发货、签收闭合、AR 结算、无未关闭 RMA/争议、请求版本正确；成功生成不可变 `closureFactId`，订单进入 `COMPLETED` 后只读。
7. **失败补偿**：签收、RMA、红字 AR/折让和完成关闭不放在一个隐式大事务里硬写跨域聚合；使用同一 Correlation ID 的补偿和事件核对。任何前置缺失都返回完整 `missingConditions`，不允许部分成功后页面显示完成。

### 验收

- 10 件全部发货后登记 8 正常、1 拒收、1 破损：签收聚合逐行可追溯，订单不能直接完成。
- 拒收/破损生成对应 RMA/折让并闭合、AR 重算结算后才允许完成。
- 重复提交签收或完成命令不重复累计；服务重启后事实仍存在。
- 无权限、跨租户、来源出库版本变化、缺证据、缺幂等键分别被拒绝。

## 5. 销售监控舱与 AI 洞察

### PRD 对齐范围

PRD 7.3.2.1、7.3.2.2 和 7.4.99 要求：

- 监控舱指标包括生效商机数、异常停滞商机、商机转订单、订单转财务。
- 订单履约延期覆盖待确认、已确认、生产补货中、部分发货状态；条件是距承诺交期不超过 3 天或已逾期，不限当前自然月。
- 时间判断使用租户时区；金额使用十进制并携带币种，不能跨币种汇总。
- 接口必须返回 `AVAILABLE / EMPTY / UNAVAILABLE`、事实时间、来源版本；缺失事实显示缺失，不能伪造 0。

### 修改方案

1. **拆分口径**：月度订单/商机统计与全量履约延期风险分成独立数据集，不再用 `monthlyOrders` 过滤交期风险。
2. **冻结月度口径**：商机转订单必须来自“报价转销售订单成功事件”；当前缺少该事件时返回 `UNAVAILABLE`，不能用订单 `createdAt` 近似。
3. **全量风险**：读取授权范围内全部未取消且状态为 `PENDING_CONFIRMATION`、`CONFIRMED`、`REPLENISHING`、`PARTIALLY_SHIPPED` 的订单；按租户时区判断今天到期或已逾期。返回稳定 `orderId`，`orderNo` 只作为展示字段。
4. **事实元信息**：响应保留 `availability`、`businessDate`、`timeZone`、`dataAsOf`、`sourceVersion`。订单空集可返回 `EMPTY` 和 0，但来源时间/版本缺失时为 `UNAVAILABLE`；金额缺失、非法或多币种冲突时不汇总为 0。
5. **补齐监控指标契约**：若当前接口继续命名为 `ai-insights`，响应必须能承载 PRD 的报价、商机、订单、财务指标；没有事实来源的指标返回 null 和缺失原因，不返回构造值。

### 验收

- 构造跨月未完成逾期订单：月度统计不包含它，履约延期风险必须包含它。
- 构造今天到期和逾期 1/8 天订单：风险等级分别为 MEDIUM、HIGH、CRITICAL。
- 多币种、缺金额、缺更新时间、空集分别验证 `UNAVAILABLE/EMPTY`，前端不得展示无风险结论。
- 稳定 ID 与展示编号分开校验，订单穿透使用稳定 ID。

## 6. 销售 SLA 触达设置

### PRD 对齐范围

PRD 7.3.2.2、销售基础数据权限和 SLA 规则要求：

- 订单 SLA 规则包含监听状态、超时阈值、通知对象、渠道、升级阈值和启停状态。
- 命中规则后生成幂等站内待办/通知任务；达到升级阈值抄送销售主管。
- 每小时扫描待确认订单；禁止直接向客户发送未审批 AI 内容。
- 基础数据配置需要 `SALES_SETTINGS_MANAGE` 或产品确认后的等价权限。

### 修改方案

1. 先补 SLA 规则 OpenAPI，字段至少包括规则 ID、租户、监听状态、超时阈值、通知对象、渠道、升级阈值、启用状态、`version`、审计字段。
2. GET 读取持久化事实；PUT/PATCH 使用权限、幂等键、乐观版本和审计，保存后必须重读返回数据库事实。
3. 新建独立扫描任务：每小时查询授权租户内超时订单，按规则生成幂等通知任务；重复扫描不重复建任务，失败进入重试和死信。
4. 前端保存成功只以后端重读结果为准；当前固定 `thresholdDays=3/reminderEnabled=true` 的响应必须下线。
5. 按 C-06 确认权限码字面值后再登记资源和角色授权。

### 验收

- 保存规则后重启读取一致；无权限用户不能读写。
- 同一超时订单重复扫描只生成一次通知任务；规则停用后不再新增。
- 达到升级阈值生成抄送任务；所有任务可追溯到订单、规则版本和操作者。

## 7. 实施顺序

1. **契约冻结**：解决 C-01 至 C-06 的产品/数据决策，输出 OpenAPI、错误码、事件和权限登记。未冻结前不写实现。
2. **来源读取模型**：先提供出库行、发货确权、AR、签收聚合、RMA 可退余量的只读查询和一致性校验，再接命令。
3. **RMA 状态机**：实现统一 transition、库存回入库事件、财务红字 AR/折让关联和关闭校验。
4. **签收与完成**：实现订单级签收命令、事件、完成检查和完成关闭。
5. **销售监控重构**：拆分月度统计与全量履约风险，补事实元信息。
6. **SLA 配置与扫描**：持久化规则、实现小时扫描和幂等通知任务。
7. **数据治理**：单独处理历史 RMA、AR、签收差异；每条事实有人工审核结论和审计。
8. **回归**：执行 PRD 第 17 章数据集，并重跑真实联调脚本。

## 8. 完成标准

只有同时满足以下条件才能宣布后端销售履约闭环完成：

1. PRD P0 命令接口、字段、错误码、事件和权限已实现；旧路径兼容方案有产品确认和下线计划。
2. `SC-FULL-005/006/011`、`AC-PH1-076/077/082` 在专用数据集上全部通过。
3. 销售、库存、生产、采购、财务五模块能通过稳定 ID、来源版本、数量和金额互相追溯。
4. 服务重启、并发冲突、重复幂等、失败补偿和越权用例通过。
5. 历史缺失事实没有自动补单；每条治理记录可审计。
6. 真实联调退出码为 0，且报告中不再存在影响销售完成关闭的阻断或严重缺口。

## 9. 暂不纳入本轮后端主流程

- 8000 端口独立 AI 服务、真实模型、SSE、RAG 和 Agent 执行仍按既有边界另行验收；销售洞察当前是规则/事实统计，不因其通过而宣称 AI 模型链路已打通。
- 外部 ERP/SRM/MES/WMS/财务系统凭证推送不属于平台内闭环；不得用外部系统缺失解释平台内 AR、RMA、签收或完成关闭事实缺失。
